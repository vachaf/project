### DB-backed log collection + analysis job 설계 문서화

- `docs/design/99_db_backed_log_collection_and_analysis_job_design.md`를 추가/갱신했다.
- 교수님 피드백을 다음 상위 운영 흐름으로 정리했다.

```text
Apache 로그 수집
  -> DB 적재
  -> 사용자의 시간 범위 기반 분석 요청
  -> Analysis Agent의 비동기 분석 실행
  -> JSON/report/viewer artifact 저장
  -> Web UI에서 상태와 결과 확인
```

- 시스템 역할을 두 agent로 분리했다.

```text
1. Log Collector Agent
   - Apache access/security/error log를 읽는다.
   - 로그를 파싱한다.
   - DB의 로그 테이블에 저장한다.
   - 수집 위치/checkpoint를 관리한다.

2. Analysis Agent
   - DB의 analysis_jobs 테이블에서 PENDING 작업을 확인한다.
   - 작업을 atomic하게 claim한 뒤 RUNNING으로 바꾼다.
   - 해당 시간 범위의 로그를 DB에서 조회한다.
   - 기존 prepare / sliding window / rollup / Stage1 / Stage2 / viewer pipeline을 실행한다.
   - 결과 artifact를 파일로 저장하고 DB에는 경로와 요약을 남긴다.
   - job 상태를 SUCCEEDED 또는 FAILED로 변경한다.
```

- 이 문서의 Agent는 별도 AI agent가 아니라 Python background worker/CLI process라는 점을 명시했다.

### analysis_jobs queue와 operator queue 분리

- 다음 기준 문장을 문서화했다.

```text
analysis_jobs는 실행 queue이고,
operator queue는 분석 결과의 검토 queue다.
두 queue는 목적과 위치가 다르다.
```

- 혼동되는 표현을 정리했다.

```text
잘못 표현될 수 있는 문장:
- Agent가 UI에서 대기 상태를 확인한다.
- Web UI queue와 Operator Queue가 같다.
- queue item이 곧 analysis job이다.

권장 표현:
- Analysis Agent는 DB의 analysis_jobs 테이블에서 status='PENDING'인 작업을 확인한다.
- UI는 DB의 analysis_jobs 상태를 읽어서 대기/작업중/완료/실패를 표시한다.
- Operator Queue는 Analysis Agent가 생성한 rollup 검토 artifact 중 하나다.
```

### MariaDB 기준 DDL 정리

- operation/control table DDL을 MariaDB/MySQL 기준으로 정리했다.

```text
- users
- analysis_jobs
- analysis_reports
- job_events
- log_collection_checkpoints
```

- 기존 로그 source table은 유지한다.

```text
- apache_access_logs
- apache_security_logs
- apache_error_logs
```

- 주요 기준:

```text
- id는 BIGINT UNSIGNED AUTO_INCREMENT를 기본 후보로 둔다.
- 시간 필드는 기존 Apache log source table과 맞춰 DATETIME(3)을 사용한다.
- 문자열 상태값은 TEXT가 아니라 VARCHAR로 제한한다.
- JSON 성격의 디버깅/상세 필드는 v1에서는 LONGTEXT 또는 TEXT로 둔다.
- 실제 제약은 MariaDB 버전 차이를 고려해 DB CHECK와 application validation 중 선택한다.
```

### 시간대 저장 원칙 정리

- DB 저장 기준:

```text
- MariaDB의 log_time / time_from / time_to는 UTC 기준의 naive DATETIME(3)로 저장한다.
- src/apache_log_shipper.py는 timezone-aware access/security timestamp를 UTC naive DATETIME(3)로 변환해 저장한다.
- error log_time도 같은 원칙으로 맞춘다.
```

- 입력/표시 기준:

```text
- Web UI의 기본 입력/표시는 Asia/Seoul로 둔다.
- 사용자가 입력한 time_from/time_to는 requested_timezone과 함께 저장 또는 기록한다.
- Analysis Agent는 UI 입력 시간을 UTC DB 조회 범위로 변환한 뒤 src/export_db_logs_cli.py에 전달한다.
```

- artifact 기준:

```text
- sliding window / rollup artifact의 사람이 읽는 label과 window_id/rollup_id는 기존 repo 흐름과 맞춰 Asia/Seoul 기준을 유지한다.
- artifact에는 DB 조회 기준과 표시 기준이 섞이지 않도록 timezone을 명시한다.
```

### apache_log_shipper.py error log UTC 저장 보정

- `src/apache_log_shipper.py`를 수정했다.
- `APACHE_ERROR_LOG_TIMEZONE` 환경변수를 추가했다.
  - 기본값: `Asia/Seoul`
- `zoneinfo.ZoneInfo`를 사용한다.
- timezone 없는 error log timestamp는 `APACHE_ERROR_LOG_TIMEZONE` 기준으로 해석한 뒤 UTC naive `DATETIME(3)`로 저장한다.
- timezone 포함 error timestamp 포맷도 수용한다.
- shipper 시작 로그에 error log timezone을 출력한다.

수정 후 핵심 동작:

```text
기존:
apache_error_logs.log_time = error log에 적힌 naive time 그대로 저장

변경 후:
apache_error_logs.log_time = error log time을 Asia/Seoul 기준으로 해석한 뒤 UTC naive DATETIME(3)로 저장
```

5. 검증 결과

### error log timestamp UTC 변환 smoke

명령:

```bash
python3 - <<'PY'
import importlib.util

spec = importlib.util.spec_from_file_location("shipper", "src/apache_log_shipper.py")
m = importlib.util.module_from_spec(spec)
spec.loader.exec_module(m)

dt = m.parse_error_time("2026-05-28 18:30:00.000")
print(dt)
print(m.to_mysql_datetime(dt))
PY
```

결과:

```text
2026-05-28 18:30:00+09:00
2026-05-28 09:30:00.000
```

해석:

```text
- error log naive timestamp를 Asia/Seoul로 해석했다.
- MariaDB 저장 문자열은 UTC naive DATETIME(3)로 변환됐다.
```
