## 1. 실험 목적

F세트 R1은 인증 endpoint에 대한 반복 interaction을 Apache 로그 표면만으로 얼마나 보수적으로 해석할 수 있는지 확인하는 실험이다.

주요 확인 축은 다음이다.

1. 단일 401 로그인 실패와 반복 401 로그인 실패를 구분하는가.
2. rapid burst와 반복 실패를 auth abuse context로 묶는가.
3. `401 -> 200` 혼재를 시계열 문맥으로 보되, 로그인 성공으로 단정하지 않는가.
4. 단독 200 또는 정상 session-like 요청을 공격으로 과승격하지 않는가.
5. POST body 미확인 한계를 Stage1/Stage2에서 유지하는가.
6. known asset IP 출발지인 점을 고려해 외부 공격자 단정을 피하는가.

## 3. prepare 개선 전/후 비교

F세트 R1 1차 실행 후, prepare 결과는 반복 401 요청을 모두 개별 candidate로 올리는 문제가 있었다. 이후 `auth_behavior_summaries`와 반복 auth candidate reduction을 추가해 동일 raw export로 재검증했다.

| 항목 | 개선 전 | 개선 후 |
|---|---:|---:|
| `candidate_rows` | 43 | 3 |
| `distinct_incident_candidates` | 43 | 3 |
| `supporting_events` | 0 | 40 |
| `auth_behavior_summaries` | 1 | 1 |
| `ip_behavior_aggregates` | 1 | 1 |
| `filtered_out_non_aggregated_rows` | 9 | 9 |
| `auth_baseline_context` | 5 | 5 |

개선 후 메타에는 다음 값이 추가로 남는다.

```text
candidate_rows_before_auth_behavior_reduction=43
auth_behavior_demoted_candidate_rows=40
candidate_rows=3
supporting_events=40
auth_behavior_summaries=1
```

해석:

- 반복 401 로그인 요청 43건 중 대표 3건만 `analysis_candidates`에 남았다.
- 나머지 40건은 `supporting_events`의 `auth_behavior_support` 문맥으로 보존됐다.
- 200 login 5건은 `auth_baseline_context`로 유지되며 candidate로 승격되지 않았다.
- 200 login row에 남던 `dir_probe:*` 혼입 문제는 제거됐다.

## 4. auth_behavior_summaries 결과

개선 후 `auth_behavior_summaries`는 F세트 R1의 핵심 문맥을 잘 보존한다.

요약:

```text
context_role=auth_behavior_context
should_promote_to_candidate=false
interpretation_limit=post_body_not_visible_no_auth_success_inference
status_counts={"401":43,"200":5}
has_repeated_401=true
has_rapid_burst=true
has_mixed_401_200=true
```

핵심 reason hints:

```text
auth_abuse:repeated_auth_endpoint
auth_abuse:repeated_401
auth_abuse:rapid_fail_burst
auth_abuse:mixed_401_200_sequence
auth_abuse:post_body_not_visible
auth_abuse:no_auth_success_inference
```

평가:

- F세트의 핵심인 반복 인증 실패와 401/200 혼재가 top-level context로 보존된다.
- 해당 summary는 `should_promote_to_candidate=false`이므로 개별 요청을 자동으로 공격 candidate로 승격하는 근거가 아니다.
- Stage2에서 이 summary를 참고해 sequence 중심으로 설명할 수 있다.

## 6. Stage2 결과 요약

Stage2는 개선 후 구조를 대체로 잘 활용했다.

주요 보고 내용:

- 동일 내부 IP `192.168.56.110`에서 `/rest/user/login` 대상 인증 실패가 짧은 시간에 반복됨.
- 후보 incident는 43건이 아니라 3건으로 축소됨.
- `auth_behavior_summaries`에서 반복 401, rapid burst, 401/200 혼재가 관찰됨.

## 8. 남은 관찰점

### 8.1 `48~51건` 표현 정리

Stage2가 auth behavior와 ip behavior를 함께 설명할 때 “48~51건 규모”처럼 다소 애매한 표현이 나올 수 있다.

향후 표현 개선 후보:

```text
auth_behavior_summary 기준으로는 48건의 auth endpoint 요청이 관찰되었고,
ip_behavior_aggregate 기준으로는 같은 시간창의 51건 요청이 포함되었다.
```

### 8.2 lab-f-set UA 언급 일반화

보고서가 `lab-f-set-*` UA를 직접 언급할 수 있다. 이는 실험 결과 설명으로는 허용되지만, 탐지 로직이 UA prefix에 의존해서는 안 된다.

향후 표현 개선 후보:

```text
실험용 UA prefix 자체가 아니라, 비브라우저성 또는 반복적 User-Agent 패턴으로 일반화해 설명한다.
```

### 8.3 Anthropic 비교는 보류

이 라운드에서는 OpenAI 기준으로 최신 구조를 확인했다. Anthropic은 별도 provider 환경/API 상태가 안정화된 뒤 동일 llm_input으로 다시 비교하는 것이 적절하다.

## 9. 결론

F세트 R1은 prepare 개선 전에는 개별 401 요청 43건이 모두 incident 후보로 올라가 Stage2 입력이 과도하게 분산되는 문제가 있었다. 개선 후에는 `auth_behavior_summaries` 중심으로 반복 인증 실패 문맥을 보존하고, 대표 3건만 candidate로 남겨 보고서 품질이 안정화됐다.

현재 결과는 F세트 R1 목적에 부합한다.

```text
- 반복 auth endpoint interaction 보존: 성공
- candidate noise 축소: 성공
- 401/200 혼재 문맥 보존: 성공
- 200 baseline 과승격 방지: 성공
- POST body 미확인 및 성공 단정 금지: 성공
```

따라서 F세트 R1은 Round 1 기준으로 “prepare + Stage1/Stage2 구조 검증 완료”로 볼 수 있다.
