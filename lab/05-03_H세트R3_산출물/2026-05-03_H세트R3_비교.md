# 2026-05-03 H세트 R3 비교

## 1. 실험 개요

- 세트: H세트 Static / Crawler / Scanner-like Noise
- 라운드: R3 — scanner-like low-signal path
- 실행 방식: Python runner
- runner: `lab/h_set/run_h_r3_scanner_low_signal.py`
- 분석 대상 raw: `lab/05-03_H세트R3_산출물/data/raw/all_2026-05-03_H_R3_kst.json`
- Stage2 결과: `openai-h_r3_scanner_low_signal_stage2_report.md`

H R3의 목적은 scanner-like / sensitive-looking path 요청이 Apache 로그 표면에 어떻게 남는지 확인하고, 이를 파일 노출·애플리케이션 존재·침해 성공으로 단정하지 않으면서 context로 보존할 수 있는지 검증하는 것이다.

이 실험은 다음을 확인하지 않는다.

- WordPress 존재 여부
- `/wp-admin/` 접근 성공 여부
- `.env` 파일 노출 여부
- `phpinfo.php` 노출 여부
- `server-status` 노출 또는 차단 성공 여부
- `backup.zip` 파일 노출 여부
- response body 원문
- 서버 내부 파일 존재 여부

---

## 2. 요청 구성

H R3 runner는 아래 scanner-like / sensitive-looking path 요청을 생성했다.

| ID | 요청 | 기대 관찰 | 해석 제한 |
|---|---|---|---|
| H-R3-01 | `GET /wp-login.php` | WordPress login-like path 요청 | WordPress 존재/취약점 단정 금지 |
| H-R3-02 | `GET /wp-admin/` | admin-like path 요청 | admin access 성공 단정 금지 |
| H-R3-03 | `GET /.env` | config-like path 요청 | `.env` 노출 성공 단정 금지 |
| H-R3-04 | `GET /phpinfo.php` | diagnostic-like path 요청 | phpinfo 노출 성공 단정 금지 |
| H-R3-05 | `GET /server-status` | server-status-like path 요청 | server-status 노출/차단 성공 단정 금지 |
| H-R3-06 | `GET /backup.zip` | backup artifact-like path 요청 | backup 노출 성공 단정 금지 |
| H-R3-07 | repeated sensitive path burst | `.env`, `server-status`, `backup.zip` 반복 | 파일 노출/침해 성공 단정 금지 |

## 4. candidate / supporting_events 결과

### 대표 candidate

대표 candidate는 `/server-status` 403 요청 1건이다.

```text
method=GET
uri=/server-status
status_code=403
verdict_hint=suspicious
user_agent=GenericScanner/1.0
```

주요 reason hints:

```text
sensitive_path:server_status
sensitive_path:no_server_status_exposure_inference
error_status:403(+2)
error_linked(+2)
no_referer_non_browser_error(+1)
```

이 candidate는 서버 상태 페이지를 노리는 정찰성 요청으로 볼 수 있지만, `403` 응답만으로 server-status 노출 성공이나 차단 성공을 확정하지 않는다.

### supporting event

나머지 `/server-status` 403 요청 1건은 supporting event로 내려갔다.

```text
supporting_role=sensitive_path_probe_support
supporting_reason=covered_by_sensitive_path_probe_summary
context_role=sensitive_path_probe_context
should_promote_to_candidate=false
interpretation_limit=sensitive_path_probe_no_file_or_app_exposure_inference
```

이 구조는 반복된 `/server-status` 요청을 개별 incident로 중복 승격하지 않고, sensitive path probing summary의 문맥으로 보존하기 위한 것이다.

## 7. probing_sequence_summaries / ip_behavior_aggregates

H R3에서는 `probing_sequence_summaries=1`과 `ip_behavior_aggregates=1`도 생성되었다.

### probing_sequence_summaries

```text
category=low_signal_dir_probe_burst
request_count=8
distinct_paths=5
status_counts={200:6, 403:2}
```

해석:

```text
여러 sensitive-looking path가 짧은 시간에 관찰된 directory probing-like context.
단, 200 text/html 반복을 민감 리소스 노출 성공으로 단정하지 않는다.
```

### ip_behavior_aggregates

```text
reason_hints=ip_behavior:multi_path_burst, ip_behavior:sensitive_path_focus
interpretation_limit=context_only_no_success_inference
```

해석:

```text
같은 src_ip에서 짧은 시간 내 여러 sensitive-looking path가 관찰된 문맥.
개별 incident 승격이나 성공 단정 근거가 아니다.
```

## 9. Stage2 결과

Stage2는 H R3 결과를 보수적으로 설명했다.

주요 해석:

- 핵심 incident는 `/server-status` 접근 1건
- severity는 `low`
- 같은 출발지에서 민감 경로를 짧은 시간에 연속 탐색
- known asset IP이므로 내부 테스트/운영 점검 가능성 병기
- `.env`, `phpinfo.php`, `backup.zip`, `wp-login`, `wp-admin` 요청은 후보 밖 탐색성 요청으로 설명
- 실제 파일 노출, 인증 성공, XSS 실행, 침해 성공은 확인되지 않음
- `403` 응답은 접근 제어 정황일 수 있지만 노출/차단 성공을 확정하지 않음

Stage2는 다음을 피했다.

- WordPress 존재 단정
- admin access 성공 단정
- `.env` 노출 성공 단정
- `phpinfo.php` 노출 성공 단정
- `server-status` 노출 또는 차단 성공 단정
- `backup.zip` 노출 성공 단정
- scanner 성공 또는 침해 성공 단정

## 11. 남은 관찰점

현재 구조는 H R3 목적에는 충분하다. 다만 후속 개선 후보는 있다.

1. supporting event의 reason_hints가 summary-level hint를 많이 포함한다.
   - 예: `/server-status` support row에 `wp_login`, `env_file`, `backup_artifact` 등이 함께 보인다.
   - `covered_by_sensitive_path_probe_summary` 문맥이 있으므로 의미상 큰 문제는 아니지만, 나중에는 row-specific hint와 summary-level hint를 분리하는 편이 더 깔끔하다.

2. `low_signal_dir_probe` category는 여전히 남는다.
   - 현재는 `sensitive_path_probe_summaries`가 별도 context를 제공하므로 큰 문제는 아니다.
   - 필요하면 `sensitive_path_probe_context` category를 후속 검토할 수 있다.

3. `/server-status` 403 대표 candidate 유지 여부
   - 현재는 representative candidate 1건을 남기는 구조가 적절하다.
   - 더 보수적으로 가려면 전체를 summary-only로 내릴 수도 있으나, 지금은 low severity candidate 1건이 더 설명력이 좋다.

## 12. 결론

H세트 R3는 목적을 달성했다.

```text
- scanner-like sensitive path 실행 성공
- sensitive_path_probe_summaries=1 생성
- /server-status 대표 candidate 1건 유지
- 나머지 server-status는 supporting_events로 보존
- wp-login/wp-admin/.env/phpinfo/backup path는 filtered context로 보존
- WordPress 존재, admin access, 파일 노출, phpinfo 노출, server-status 노출/차단, backup 노출, 공격 성공 단정 없음
- Stage2는 suspicious_scan low로 보수적으로 설명
```

따라서 H R3는 완료로 본다.
