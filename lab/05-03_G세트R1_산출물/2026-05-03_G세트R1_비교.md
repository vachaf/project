# 2026-05-03 G세트 R1 비교

## 1. 실험 개요

- 세트: G세트 HTTP Method / Protocol Anomaly
- 라운드: R1 — 기본 method probing
- 실행 방식: Python runner
- runner: `lab/g_set/run_g_r1_method_probe.py`
- 분석 대상 raw: `lab/05-03_G세트R1_산출물/data/raw/security_2026-05-03_G_R1_kst.json`
- Stage2 결과: `openai-g_r1_method_behavior_stage2_report.md`

G R1의 목적은 `OPTIONS`, `TRACE`, `PUT`, `DELETE`, `HEAD`, `GET` 요청이 Apache 로그 표면에 어떻게 남는지 확인하고, 파이프라인이 이를 성공 단정 없이 method behavior context로 보존할 수 있는지 검증하는 것이다.

이 실험은 다음을 확인하지 않는다.

- `TRACE` / XST 성공 여부
- `PUT` 파일 업로드 성공 여부
- `DELETE` 리소스 삭제 성공 여부
- `OPTIONS` 기반 CORS 취약 여부
- 서버 내부 설정
- response body 원문
- request body 원문

---

## 2. 요청 구성

G R1 runner는 아래 6개 요청을 생성했다.

| ID | 요청 | 관찰 결과 | 해석 제한 |
|---|---|---:|---|
| G-R1-01 | `OPTIONS /` | `204`, `0B` | CORS 취약점 단정 금지 |
| G-R1-02 | `TRACE /` | `405`, `302B` | XST 성공/차단 성공 단정 금지 |
| G-R1-03 | `PUT /upload/g_probe.txt` | `200`, `75002B` | 파일 업로드 성공 단정 금지 |
| G-R1-04 | `DELETE /api/resource/g_probe` | `500`, `3045B` | 리소스 삭제 성공/실패 단정 금지 |
| G-R1-05 | `HEAD /` | `200`, `0B` | 정상 baseline 가능성 |
| G-R1-06 | `GET /` | `200`, `75002B` | 정상 baseline 가능성 |

`PUT`의 `200`과 큰 응답 크기는 관찰 가능한 Apache 표면 신호일 뿐이며, 파일 생성 또는 write 성공의 근거로 사용하지 않는다.

## 3. 최초 prepare 결과와 문제점

초기 prepare 결과에서는 6개 요청이 모두 후보 밖으로 분류되었다.

```text
candidate_rows=0
supporting_events=0
filtered_out_rows=6
method_behavior_summaries 없음
```

각 row는 모두 다음처럼 정리되었다.

```text
noise_category=low_signal_fuzzing
reason_hints=dir_probe:burst
```

이 상태는 G R1의 1차 실행 자체는 성공했음을 보여주지만, G세트의 핵심인 HTTP method behavior를 충분히 보존하지 못했다. 특히 `OPTIONS`, `TRACE`, `PUT`, `DELETE`, `HEAD`, `GET`이 모두 `dir_probe:burst` 하나로만 표현되어 Stage2가 method/protocol 문맥을 명확히 설명하기 어려웠다.

## 4. 개선 후 prepare 결과

`method_behavior_summaries`를 추가한 뒤 동일 raw를 다시 prepare 했다.

```text
total_exported_rows=6
candidate_rows=0
distinct_incident_candidates=0
supporting_events=0
filtered_out_rows=6
ip_behavior_aggregates=0
auth_behavior_summaries=0
method_behavior_summaries=1
```

개선 후에도 개별 요청은 candidate로 과승격되지 않았다. 대신 6개 method 요청이 `method_behavior_summaries` 1건으로 context-only 보존되었다.

요약 내용은 다음과 같다.

```text
context_role=method_behavior_context
should_promote_to_candidate=false
interpretation_limit=no_method_success_inference_from_apache_logs
request_count=6
method_counts={DELETE:1, GET:1, HEAD:1, OPTIONS:1, PUT:1, TRACE:1}
status_counts={200:3, 204:1, 405:1, 500:1}
risky_methods_observed=[OPTIONS, TRACE, PUT, DELETE]
baseline_methods_observed=[HEAD, GET]
```

reason hints도 method 문맥에 맞게 정리되었다.

```text
method_probe:options
method_probe:trace
method_probe:put
method_probe:delete
method_probe:destructive_method
baseline:normal_head
baseline:normal_get
method_probe:mixed_method_sequence
method_probe:no_method_success_inference
```

## 5. Stage1 결과

G R1에서는 `analysis_candidates=0`이므로 Stage1에서 처리한 candidate는 없다.

```text
processed_candidate_count=0
success_count=0
error_count=0
```

이는 실패가 아니다. 이번 라운드는 개별 method request를 incident로 승격하기보다, `method_behavior_summaries`를 통해 context-only로 보존하는 것이 목적이기 때문이다.

---

## 6. Stage2 결과

Stage2는 `method_behavior_summaries`를 기반으로 다음을 보수적으로 설명했다.

- 전체 6건 모두 후보 밖 저신호 요청으로 분류됨
- 고신호 incident 없음
- 동일 `src_ip`에서 짧은 시간 안에 여러 HTTP method가 관찰됨
- `OPTIONS`, `TRACE`, `PUT`, `DELETE`는 method probing 또는 내부 점검 가능성으로 설명
- `HEAD`, `GET`은 baseline method로 분리
- known asset IP와 일치하므로 내부 테스트/운영 점검 가능성 병기
- 업로드 성공, 삭제 성공, XST 성공, CORS 취약점 성공을 단정하지 않음

보고서의 핵심 해석은 다음 방향으로 적절했다.

```text
침해 성공보다는 내부 자산에서 관찰된 메서드 탐색성 요청으로 요약하는 것이 정확하다.
즉시 필요한 조치는 공격 차단보다 출발지의 정체와 운영 목적 확인이다.
```

## 7. 체크포인트 평가

| 체크포인트 | 평가 | 비고 |
|---|---:|---|
| `OPTIONS` 보존 | 통과 | `method_probe:options`로 context 보존 |
| `TRACE` 보존 | 통과 | `method_probe:trace`, XST 성공 단정 없음 |
| `PUT` 보존 | 통과 | `method_probe:put`, 파일 업로드 성공 단정 없음 |
| `DELETE` 보존 | 통과 | `method_probe:delete`, 삭제 성공 단정 없음 |
| `HEAD` baseline 분리 | 통과 | `baseline:normal_head` |
| `GET` baseline 분리 | 통과 | `baseline:normal_get` |
| candidate 과승격 방지 | 통과 | `candidate_rows=0` 유지 |
| Stage2 method context 설명 | 통과 | method behavior context 섹션 생성 |
| known asset 고려 | 통과 | 내부 테스트/운영 점검 가능성 병기 |
| response/request body 미사용 | 통과 | 성공 단정 없음 |

## 8. 남은 관찰점

현재 구조는 R1 목적에는 충분하다. 다만 이후 G세트 확장을 위해 다음은 후속 검토 대상이다.

1. `filtered_out_breakdown`은 여전히 `low_signal_fuzzing=6`으로 남는다.
   - 현재는 `method_behavior_summaries`가 별도 context를 제공하므로 문제는 아니다.
   - 나중에 필요하면 `method_behavior_context` 또는 `method_baseline_context`로 noise category를 세분화할 수 있다.

2. Stage1은 candidate가 없으므로 method verdict를 평가하지 않는다.
   - 이번 R1에서는 의도된 동작이다.
   - 향후 `TRACE/PUT/DELETE` 대표 row를 Stage1 candidate로 올릴지 여부는 별도 판단이 필요하다.

3. G R2 malformed/protocol anomaly는 아직 실행하지 않았다.
   - R2에서는 malformed request가 `security`, `access`, `error` 중 어디에 남는지가 핵심 관찰점이다.

## 9. 결론

G세트 R1은 목적을 달성했다.

```text
- runner 기반 method probing 실행 성공
- Apache 로그에 OPTIONS/TRACE/PUT/DELETE/HEAD/GET 보존 확인
- 최초 prepare의 dir_probe:burst 뭉개짐 문제 확인
- 개선 후 method_behavior_summaries=1 생성
- candidate 과승격 없이 context-only 보존
- HEAD/GET baseline 분리
- PUT/DELETE/TRACE/OPTIONS 성공 단정 없음
- Stage2가 method behavior context를 보수적으로 설명
```

따라서 G R1은 완료로 본다.
