# 2026-05-03 H세트 R1 비교

## 1. 실험 개요

- 세트: H세트 Static / Crawler / Scanner-like Noise
- 라운드: R1 — Static / health baseline
- 실행 방식: Python runner
- runner: `lab/h_set/run_h_r1_static_baseline.py`
- 분석 대상 raw: `lab/05-03_H세트R1_산출물/data/raw/all_2026-05-03_H_R1_kst.json`
- Stage2 결과: `openai-h_r1_static_baseline_stage2_report.md`

H R1의 목적은 favicon, robots.txt, sitemap.xml, static asset, health check, normal GET 요청이 Apache 로그 표면에서 어떻게 남는지 확인하고, 이를 공격 candidate로 과승격하지 않는지 검증하는 것이다.

이 실험은 다음을 확인하지 않는다.

- static file 실제 존재 여부
- robots.txt / sitemap.xml 내용
- JavaScript 실행 여부
- CSS/image 파일 내용
- health endpoint 정상 여부
- 파일 노출 성공 여부
- 브라우저 렌더링 여부

|---|---|---|---|

| H-R1-04 | `GET /assets/app.js` | JS static path 요청 | JS 실행/XSS 단정 금지 |

| H-R1-07 | `GET /api/health` | health-like endpoint 요청 | health 정상/장애 확정 금지 |

## 4. 최초 prepare 문제와 개선 방향

초기 H R1 prepare 결과에서는 static/baseline 요청들이 candidate로 올라가지는 않았지만, 모든 filtered row의 reason hint가 `dir_probe:burst`로만 남았다.

초기 상태:

```text
candidate_rows=0
filtered_out_rows=8
static_baseline_summaries 없음
filtered row reason_hints=dir_probe:burst
```

이 상태는 H세트의 핵심인 static / health / normal browse baseline 문맥을 충분히 보존하지 못했다. 특히 favicon, robots, sitemap, JS/CSS/image asset, health check를 directory probing burst와 같은 표현으로만 남기는 것은 부정확했다.

개선 방향은 `static_baseline_summaries`와 baseline-specific reason hints를 추가하는 것이었다.

## 6. filtered_out reason_hints 개선

filtered row의 reason hints는 static/baseline 문맥에 맞게 정리되었다.

| 요청 | category | reason_hints |
|---|---|---|
| `/favicon.ico` | `benign_normal_search` | `baseline:favicon`, `baseline:static_asset` |
| `/robots.txt` | `benign_normal_search` | `baseline:robots_txt`, `baseline:no_crawler_policy_inference` |
| `/sitemap.xml` | `benign_normal_search` | `baseline:sitemap_xml`, `baseline:no_site_structure_inference` |
| `/assets/app.js` | `benign_normal_search` | `baseline:static_asset`, `baseline:static_js`, `baseline:no_js_execution_inference` |
| `/assets/style.css` | `benign_normal_search` | `baseline:static_asset`, `baseline:static_css` |
| `/images/logo.png` | `benign_normal_search` | `baseline:static_asset`, `baseline:static_image`, `baseline:no_file_exposure_inference` |
| `/api/health` | `low_signal_fuzzing` | `baseline:health_check`, `baseline:no_health_status_inference` |
| `/` | `benign_normal_search` | `baseline:normal_get` |

`/api/health`는 `500` 응답이므로 `low_signal_fuzzing`으로 남았지만, `baseline:health_check`와 `baseline:no_health_status_inference`가 붙어 health endpoint 정상/장애 단정을 피할 수 있게 되었다.

## 8. Stage2 결과

Stage2는 H R1 결과를 보수적으로 설명했다.

주요 해석:

- 확정적인 침해 사건 없음
- 16개 수집 row 중 후보 사건 0건
- 대부분은 정상 비교군 또는 static baseline context
- `192.168.56.1`은 known asset이므로 내부 테스트/운영 점검 가능성 병기
- `/api/health`의 `500`은 관찰되었으나 오류 원인이나 침해 성공을 단정하지 않음
- static file 존재, robots/sitemap 내용, JS 실행, file exposure, health 정상 여부를 단정하지 않음

Stage2는 다음을 피했다.

- static file 노출 성공 단정
- robots.txt 정책 내용 단정
- sitemap 기반 사이트 구조 노출 단정
- JavaScript 실행 또는 XSS 단정
- image/file exposure 단정
- health endpoint 정상/장애 확정
- multi-path burst만으로 공격 확정

## 10. 남은 관찰점

현재 구조는 H R1 목적에는 충분하다. 다만 후속 개선 후보는 있다.

1. `/api/health` 500이 `low_signal_fuzzing`으로 남는다.
   - 현재는 `baseline:health_check`, `baseline:no_health_status_inference`가 붙어 있어 큰 문제는 아니다.
   - 나중에 필요하면 `health_check_error_context` 또는 `health_check_baseline` category를 검토할 수 있다.

2. static baseline row 중 다수가 `benign_normal_search` category를 사용한다.
   - 기능적으로는 정상 비교군 역할을 하고 있으므로 현재 문제는 작다.
   - 표현상 더 명확히 하려면 `static_asset_baseline` / `normal_static_baseline` category를 후속 검토할 수 있다.

3. `ip_behavior_aggregates=1`이 생성된다.
   - 8개 path가 짧은 시간에 관찰되어 생긴 context다.
   - `interpretation_limit=context_only_no_success_inference`가 유지되므로 문제는 아니다.
   - Stage2도 이를 공격 확정으로 보지 않았다.

## 11. 결론

H세트 R1은 목적을 달성했다.

```text
- static / health / normal browse baseline 실행 성공
- candidate_rows=0 유지
- static_baseline_summaries=1 생성
- favicon/robots/sitemap/static asset/health/normal GET이 baseline context로 보존됨
- static file 존재, robots/sitemap 내용, JS 실행, file exposure, health 정상 여부 단정 없음
- Stage2가 known asset 기반 내부 테스트/운영 점검 가능성을 병기하며 보수적으로 설명
```

따라서 H R1은 완료로 본다.
