# 2026-05-03 G세트 종합 비교

## 1. 문서 목적

이 문서는 G세트 HTTP Method / Protocol Anomaly 실험의 R1/R2/R3 결과를 종합한다.

G세트의 목적은 Apache 로그 표면에서 HTTP method / protocol 관련 이상 행동을 보수적으로 해석할 수 있는지 확인하는 것이다.

핵심 질문은 다음이다.

```text
1. OPTIONS / TRACE / PUT / DELETE / HEAD / GET 같은 method 사용이 Apache 로그에 어떻게 남는가?
2. malformed / protocol-like 요청이 access/security/error 중 어디에 남는가?
3. 정상 baseline 또는 monitoring-like 요청이 공격 candidate로 과승격되지 않는가?
4. Stage2가 method/protocol 성공을 단정하지 않고 context-only로 설명하는가?
```

G세트는 성공한 공격을 증명하는 실험이 아니다. 특히 다음은 단정하지 않는다.

- PUT 업로드 성공
- DELETE 삭제 성공
- TRACE / XST 성공
- OPTIONS / CORS 취약점 성공
- malformed request 우회 성공
- protocol bypass 성공
- 서버 침해 성공

---

## 2. 전체 결론

G세트 R1/R2/R3는 전체적으로 목적을 달성했다.

```text
G R1: method probing 요청을 method_behavior_summaries로 context-only 보존
G R2: protocol / malformed request를 protocol_anomaly_summaries로 context-only 보존
G R3: 정상 baseline / FP bait 요청이 candidate로 과승격되지 않음을 확인
```

가장 중요한 결과는 다음이다.

```text
- G R1/R2/R3 모두 candidate 과승격을 피했다.
- Stage2는 method/protocol 관련 성공을 단정하지 않았다.
- HEAD/GET baseline은 정상 또는 비교 문맥으로 보존됐다.
- malformed/protocol 요청은 고신호 incident가 아니라 context-only summary로 보존됐다.
```

## 4. G R1 요약 — 기본 method probing

### 4.1 목적

G R1은 `OPTIONS`, `TRACE`, `PUT`, `DELETE`, `HEAD`, `GET` 요청이 Apache 로그에 어떻게 남는지 확인했다.

### 4.2 관찰된 요청

```text
OPTIONS / -> 204
TRACE / -> 405
PUT /upload/g_probe.txt -> 200
DELETE /api/resource/g_probe -> 500
HEAD / -> 200
GET / -> 200
```

### 4.3 최초 prepare 문제

초기 prepare에서는 6개 요청이 모두 아래처럼 정리되었다.

```text
candidate_rows=0
filtered_out_rows=6
method_behavior_summaries 없음
reason_hints=dir_probe:burst
```

이 상태는 method/protocol 문맥을 충분히 전달하지 못했다.

### 4.4 개선 후 결과

`method_behavior_summaries`를 추가한 뒤 다음처럼 정리되었다.

```text
candidate_rows=0
filtered_out_rows=6
method_behavior_summaries=1
```

summary 핵심:

```text
method_counts={DELETE:1, GET:1, HEAD:1, OPTIONS:1, PUT:1, TRACE:1}
status_counts={200:3, 204:1, 405:1, 500:1}
risky_methods_observed=[OPTIONS, TRACE, PUT, DELETE]
baseline_methods_observed=[HEAD, GET]
```

reason hints:

```text
method_probe:options
method_probe:trace
method_probe:put
method_probe:delete
method_probe:destructive_method
baseline:normal_head
baseline:normal_get
method_probe:mixed_method_sequence
method_probe:no_method_success_inference
```

### 4.5 판단

G R1은 성공이다.

```text
- method probing 요청이 사라지지 않고 context로 보존됨
- HEAD/GET baseline 과승격 없음
- PUT/DELETE/TRACE/OPTIONS 성공 단정 없음
- Stage2가 method behavior context를 설명함
```

```text

```

## 5. G R2 요약 — protocol / malformed request

### 5.1 목적

G R2는 raw socket 기반 runner로 protocol / malformed request-like 요청이 Apache 로그 표면에 어떻게 남는지 확인했다.

### 5.2 관찰 대상

```text
FAKEMETHOD
HTTP/1.0 request
bad protocol version
missing Host
odd Host
long path
```

### 5.3 raw export 결과

```text
total_count=12
access=6
security=6
error=0
```

이번 실행에서는 malformed/protocol 요청이 `access`와 `security` 표면에 남았고, `error` row는 생성되지 않았다.

### 5.4 최초 prepare 문제

초기 prepare에서는 일부 요청이 다음처럼 정리되었다.

```text
FAKEMETHOD -> method_probe:unsupported_method
HTTP/1.0 -> baseline:normal_get
bad protocol -> baseline:normal_get
missing Host -> baseline:normal_get
odd Host -> baseline:normal_get
long path -> baseline:normal_get
```

이 상태는 G R2 목적에는 부족했다. `bad_protocol`, `missing_host`, `odd_host`, `long_path`는 정상 GET baseline이라기보다 protocol anomaly context로 보존되어야 한다.

### 5.5 개선 후 결과

`protocol_anomaly_summaries`를 추가한 뒤 다음처럼 정리되었다.

```text
candidate_rows=0
filtered_out_rows=6
ip_behavior_aggregates=1
method_behavior_summaries=1
protocol_anomaly_summaries=1
```

summary 핵심:

```text
context_role=protocol_anomaly_context
should_promote_to_candidate=false
interpretation_limit=protocol_anomaly_context_only_no_success_inference
status_counts={200:3, 400:3}
method_counts={GET:5, FAKEMETHOD:1}
anomaly_types_observed=[unsupported_method, http10_request, bad_protocol_version, missing_host, odd_host, long_path]
```

reason hints:

```text
method_probe:unsupported_method
protocol_anomaly:unsupported_method
protocol_anomaly:malformed_request
protocol_anomaly:http10_request
protocol_anomaly:legacy_protocol_observation
protocol_anomaly:bad_protocol_version
protocol_anomaly:missing_host
protocol_anomaly:odd_host
protocol_anomaly:long_path
protocol_anomaly:no_success_inference
```

### 5.6 판단

G R2는 성공이다.

```text
- malformed/protocol request가 context-only로 보존됨
- candidate 과승격 없음
- protocol bypass / malformed request 우회 / 서버 침해 성공 단정 없음
- Stage2가 protocol anomaly context를 보수적으로 설명함
```

```text
lab/05-03_G세트R2_산출물/2026-05-03_G세트R2_비교.md
```

## 6. G R3 요약 — baseline / FP bait

### 6.1 목적

G R3는 정상 또는 점검성 HTTP method 요청이 공격 candidate로 과승격되지 않는지 확인했다.

### 6.2 관찰 대상

```text
HEAD /health
browser-like OPTIONS /
normal GET /
InternalMonitor GET /
repeated HEAD / x3
```

### 6.3 prepare 결과

```text
total_exported_rows=14
selected_source_rows=7
candidate_rows=0
filtered_out_rows=7
noise_group_count=1
method_behavior_summaries=1
protocol_anomaly_summaries=0
```

method summary 핵심:

```text
method_counts={HEAD:4, GET:2, OPTIONS:1}
status_counts={200:6, 204:1}
risky_methods_observed=[OPTIONS]
baseline_methods_observed=[HEAD, GET]
```

### 6.4 Stage2 결과

Stage2는 다음처럼 보수적으로 설명했다.

```text
- 고신호 incident 없음
- 정상 HEAD/GET 중심 baseline 요청
- browser-like OPTIONS는 CORS 취약점 단정 없이 preflight-like context로 설명
- InternalMonitor UA는 내부 테스트/운영 점검 가능성으로 설명
- repeated HEAD는 공격 단정 없이 저신호 점검성 문맥으로 설명
```

### 6.5 판단

G R3는 성공이다.

```text
- 정상 method / baseline 요청이 candidate로 과승격되지 않음
- protocol anomaly 오탐 없음
- CORS 취약점, method 허용, 공격 성공 단정 없음
- Stage2가 baseline / FP bait를 보수적으로 설명함
```

## 8. 주요 개선 효과

G세트 진행 중 도입된 핵심 개선은 두 가지다.

### 8.1 method_behavior_summaries

역할:

```text
OPTIONS/TRACE/PUT/DELETE/HEAD/GET 같은 method usage를 success assertion 없이 context로 보존한다.
```

효과:

```text
- method 요청이 dir_probe:burst로만 뭉개지지 않음
- HEAD/GET baseline과 risky method를 함께 설명 가능
- Stage2가 method probing / baseline comparison context를 설명 가능
```

### 8.2 protocol_anomaly_summaries

역할:

```text
invalid method, bad protocol, missing/odd Host, long path를 protocol anomaly context로 보존한다.
```

효과:

```text
- malformed/protocol 요청이 baseline:normal_get으로만 정리되지 않음
- Stage2가 protocol parsing / malformed request context를 설명 가능
- protocol bypass 또는 침해 성공 단정을 피하면서도 관찰 문맥 유지
```

## 10. 남은 개선 후보

현재 G세트 결과는 충분히 안정적이다. 다만 다음 표현 개선 후보가 남아 있다.

### 10.1 `low_signal_fuzzing` category 세분화

R1/R2/R3 모두 일부 filtered row는 여전히 `low_signal_fuzzing`으로 남는다.

후보:

```text
method_behavior_context
protocol_anomaly_context
normal_method_baseline
monitoring_baseline
preflight_context
```

현재는 top-level summary가 해당 문맥을 보존하므로 급한 문제는 아니다.

### 10.2 repeated HEAD monitoring 표현 개선

G R3에서 repeated `HEAD` monitoring은 `low_signal_fuzzing`으로 집계된다.

더 자연스러운 표현 후보:

```text
monitoring_baseline
baseline:repeated_head_monitoring
```

다만 candidate로 올라가지 않고 Stage2도 점검성 가능성을 병기하므로 즉시 수정 필요는 낮다.

### 10.3 Stage1 candidate 없음의 의미 정리

G세트는 candidate가 없는 라운드가 많다.

```text
G R1: candidate 0
G R2: candidate 0
G R3: candidate 0
```

이는 실패가 아니라 `method_behavior_summaries` / `protocol_anomaly_summaries` 기반 context-only 분석이 의도대로 동작한 것이다.

## 11. 결론

G세트는 완료로 본다.

```text
- R1: method probing context 보존 성공
- R2: protocol anomaly context 보존 성공
- R3: baseline / FP bait 과승격 방지 성공
- 모든 라운드에서 성공/침해/우회 단정 없음
- Stage2는 context-only summary를 활용해 보수적으로 설명함
```

따라서 G세트는 HTTP method/protocol surface behavior를 Apache 로그만으로 보수적으로 요약하는 실험 목표를 달성했다.
