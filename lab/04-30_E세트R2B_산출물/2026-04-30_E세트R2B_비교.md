## 1. 결론

E세트 R2B는 성공으로 본다.

이번 라운드의 목적은 기존 E세트 R2에서 보강한 PHP wrapper/file disclosure 탐지가 `route=`와 `path=`에만 묶이지 않고, 다른 parameter name과 payload 변형에서도 일반화되는지 확인하는 것이었다.

결과적으로 `file=`, `path=`, `route=` 세 변형 모두 `suspicious_file_disclosure` candidate로 보존되었다. 특히 `convert.base64-encode`가 없는 `route=php://filter/resource=config.php`도 `php_filter_wrapper + resource_parameter + config_php` 조합으로 candidate가 되었다.

동시에 control 요청인 `/config.php`, `/admin/config.php` 직접 접근은 candidate로 과승격되지 않고 `low_signal_dir_probe`로 분리되었다. 이 점은 R2B의 또 다른 목표였던 과탐 억제 측면에서도 적절하다.

요약:

```text
total_exported_rows=6
candidate_rows=4
filtered_out_rows=2
supporting_events=0
probing_sequence_summaries=1
stage1_success_count=4
stage1_error_count=0
```

OpenAI Stage2도 PHP wrapper 기반 파일 노출 시도 정황으로 해석하면서, Apache 로그만으로 실제 config/source 내용 노출 성공은 확정하지 않았다.

| 구분 | 요청 | 기대 역할 | 최종 처리 |

## 3. Prepare 결과

### 3.1 Count

`llm_input` 기준 count는 다음과 같다.

```text
total_exported_rows=6
selected_source_rows=6
candidate_rows_before_dedup=4
candidate_rows=4
filtered_out_rows=2
supporting_events=0
false_positive_review_candidates=0
probing_sequence_summaries=1
```

filtered out 분포:

```text
low_signal_dir_probe=2
```

해석:

- wrapper 요청은 candidate로 보존되었다.
- direct config path control은 filtered/context로 분리되었다.
- 동일 시간대의 `/index.php`, `/config.php`, `/admin/config.php` 흐름은 `probing_sequence_summaries`로 context-only 보존되었다.

### 3.2 E-14: `file=` 기반 wrapper

요청:

```text
/index.php?file=php://filter/convert.base64-encode/resource=config.php
```

전처리 결과:

```text
verdict_hint=suspicious_file_disclosure
score=12
status_code=200
response_body_bytes=32777
resp_content_type=text/html
```

핵심 hint:

```text
file_disclosure:php_filter_wrapper
file_disclosure:base64_source_intent
file_disclosure:resource_parameter
file_disclosure:sensitive_resource:config_php
long_query(+1)
```

평가:

- 기존 `route=`, `path=` 외에 `file=` parameter에서도 PHP wrapper intent가 탐지되었다.
- `config.php` 대상과 `base64-encode` source disclosure 의도가 함께 보존되었다.
- 200/text/html과 약 32KB 응답은 성공 근거가 아니라 추가 확인이 필요한 보조 지표다.

### 3.3 E-15: `admin/config.php` 대상 wrapper

요청:

```text
/index.php?path=php://filter/convert.base64-encode/resource=admin/config.php
```

전처리 결과:

```text
verdict_hint=suspicious_file_disclosure
score=12
status_code=200
response_body_bytes=32783
resp_content_type=text/html
```

핵심 hint:

```text
file_disclosure:php_filter_wrapper
file_disclosure:base64_source_intent
file_disclosure:resource_parameter
file_disclosure:sensitive_resource:admin_config_php
long_query(+1)
```

평가:

- `admin/config.php` 대상으로도 file disclosure intent가 보존되었다.
- direct `/admin/config.php` 접근과 달리 wrapper 기반 접근이므로 candidate로 올리는 것이 맞다.
- 실제 admin config 내용 노출 성공은 Apache 로그만으로 확정할 수 없다.

### 3.4 E-16: base64 없는 lightweight wrapper

요청:

```text
/index.php?route=php://filter/resource=config.php
```

전처리 결과:

```text
verdict_hint=suspicious_file_disclosure
score=12
status_code=404
response_body_bytes=19832
resp_content_type=text/html
```

핵심 hint:

```text
file_disclosure:php_filter_wrapper
file_disclosure:resource_parameter
file_disclosure:sensitive_resource:config_php
error_status:404(+2)
no_referer_non_browser_error(+1)
```

평가:

- `convert.base64-encode`가 없어도 `php://filter + resource=config.php` 조합만으로 candidate가 되었다.
- 이는 R2B에서 확인하려던 일반화 포인트다.
- 404이므로 실제 파일 노출 성공보다는 시도 정황으로 보는 것이 맞다.
- 동일 UA로 2회 기록되었으나 두 요청 모두 별도 request_id를 가진 정상 수집 row다.

### 3.5 E-17: direct config control

요청:

```text
/config.php
/admin/config.php
```

전처리 결과:

```text
noise_category=low_signal_dir_probe
response_body_bytes=0
resp_content_type=text/html
```

핵심 hint:

```text
dir_probe:burst
dir_probe:sensitive_path
dir_probe:sensitive_config_path
file_probe:config_php
file_probe:admin_config_php
dir_probe:admin_path
```

평가:

- direct config path control이 candidate로 과승격되지 않은 것은 적절하다.
- `response_body_bytes=0`이므로 파일 내용 노출 근거가 없다.
- PHP 설정 파일은 실행되더라도 출력이 없을 수 있으므로 “안전” 또는 “성공” 어느 쪽으로도 단정하지 않는다.

## 4. Stage1 결과

OpenAI Stage1은 candidate 4건을 모두 처리했고 error는 없었다.

```text
processed_candidate_count=4
success_count=4
error_count=0
verdicts={"suspicious_path_traversal": 4}
severities={"medium": 4}
```

Stage1은 각 요청을 모두 PHP wrapper 기반 파일 읽기/소스 노출 시도로 설명했다.

좋은 점:

- `php://filter` 의미를 인식했다.
- `resource=config.php`, `resource=admin/config.php`를 민감 자원 접근으로 보았다.
- `convert.base64-encode`를 source disclosure 의도와 연결했다.
- 200/text/html 또는 404를 실제 파일 노출 성공으로 단정하지 않았다.

남은 한계:

- 최종 verdict는 여전히 `suspicious_path_traversal`로 수렴했다.
- prepare의 `verdict_hint=suspicious_file_disclosure`와 Stage1 설명은 file disclosure에 가깝지만, Stage1 verdict taxonomy가 이를 별도 verdict로 표현하지 못하고 path traversal에 흡수하는 상태다.

후속 개선 후보:

```text
suspicious_file_disclosure
suspicious_source_disclosure
suspicious_lfi
```

중 하나를 Stage1 verdict 후보로 정식화하는 방안을 검토한다.

## 5. Stage2 결과

OpenAI Stage2의 전체 제목은 다음과 같다.

```text
Apache 웹 로그 2차 분석 요약: known asset IP에서 관찰된 PHP 래퍼 기반 파일 노출 시도 정황
```

Stage2는 이번 구간을 다음처럼 요약했다.

- 총 6건 중 4건이 후보 incident
- 모든 후보는 동일 출발지 IP `192.168.56.109`에서 발생
- 해당 IP는 known asset으로 매칭
- 주요 패턴은 `/index.php`에 대한 `php://filter` 및 `convert.base64-encode` 기반 파일 읽기/소스 노출 시도
- `/config.php`, `/admin/config.php` 직접 지정은 민감 설정 경로 probing context
- Apache 로그만으로 실제 파일 내용 노출 성공은 확인 불가

평가:

- Stage2는 R2B의 핵심을 제대로 요약했다.
- 200/text/html을 성공 근거로 쓰지 않았다.
- known asset IP이므로 내부 테스트/운영 점검 가능성을 병기했다.
- 후보 밖 `low_signal_dir_probe` 2건을 incident로 승격하지 않고 context로만 설명했다.

## 6. OpenAI 판단의 적절성

### 6.1 잘 된 점

1. PHP wrapper variant를 모두 파일 노출 시도로 해석했다.
2. `base64-encode`가 있는 요청을 source disclosure intent로 설명했다.
3. base64 없는 wrapper도 `php://filter/resource=config.php`로 의미를 잡았다.
4. 200 응답과 큰 응답 크기를 성공 근거로 단정하지 않았다.
5. 404 요청은 실패 또는 시도 정황으로 제한했다.
6. direct config path control을 별도 low-signal probing context로 분리했다.

### 6.2 아쉬운 점

1. Stage1 verdict가 `suspicious_path_traversal`로 고정되었다.
2. `suspicious_file_disclosure`가 verdict로 정식화되어 있지 않아 기법 분류가 덜 정확하다.
3. 동일 UA의 no-base64 wrapper가 2회 기록되어 문서상 중복처럼 보일 수 있다. 다만 request_id가 다르므로 데이터 오류는 아니다.

## 7. Juice Shop / OpenCart 관점 차이

| 항목 | Juice Shop | OpenCart E R2B |
|---|---|---|
| 앱 구조 | Node/SPA/API 중심 | PHP/OpenCart `index.php` 중심 |
| 주요 payload 위치 | REST query, path | `file=`, `path=`, `route=` query parameter |
| 주요 위협 | SQLi/XSS/traversal | PHP wrapper file/source disclosure |
| 성공 판단 주의점 | SPA fallback HTML | PHP routing/template/empty output |
| 직접 config path | 일반 probing에 가까움 | 실제 PHP 설정 파일 경로일 수 있음 |
| 핵심 해석 | API query/payload 탐지 | wrapper/file disclosure intent 탐지 |

R2B는 OpenCart/PHP 환경에서만 의미 있는 payload를 다루지만, 코드 개선은 OpenCart 전용이 아니다. `php://filter`, `resource=`, `convert.base64-encode`, `config.php`와 같은 일반 PHP/file disclosure 신호를 사용한다.

## 8. 최종 평가

E세트 R2B는 prepare, Stage1, Stage2 기준 모두 성공이다.

성공 근거:

1. `file=php://filter...config.php`가 candidate로 보존되었다.
2. `path=php://filter...admin/config.php`가 candidate로 보존되었다.
3. `route=php://filter/resource=config.php`가 base64 없이도 candidate로 보존되었다.
4. direct `/config.php`, `/admin/config.php`는 candidate로 과승격되지 않았다.
5. `probing_sequence_summaries`가 context-only로 생성되었다.
6. OpenAI Stage1/Stage2는 실제 파일 노출 성공을 단정하지 않았다.
7. known asset IP로 내부 테스트 가능성을 병기했다.

남은 개선점:

1. `suspicious_file_disclosure` Stage1 verdict 정식화 필요.
2. no-base64 wrapper가 동일 UA로 2회 기록된 점은 문서에서 중복 실행으로 명시.
3. direct config path 200/0B는 계속 context-only로 두되, 향후 hint를 더 세분화할 수 있다.
4. Claude provider는 미실행이므로 provider 비교는 불완전하다.
