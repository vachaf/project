# 2026-05-03 G세트 R3 비교

## 1. 실험 개요

- 세트: G세트 HTTP Method / Protocol Anomaly
- 라운드: R3 — baseline / FP bait
- 실행 방식: Python runner
- runner: `lab/g_set/run_g_r3_baseline.py`
- 분석 대상 raw: `lab/05-03_G세트R3_산출물/data/raw/all_2026-05-03_G_R3_kst.json`
- Stage2 결과: `openai-g_r3_baseline_stage2_report.md`

G R3의 목적은 정상 또는 점검성 HTTP method 요청이 `method_probe` / `protocol_anomaly` / incident 후보로 과승격되지 않는지 확인하는 것이다.

이 실험은 다음을 확인하지 않는다.

- CORS 취약점 여부
- method 허용 여부
- 서버 설정 취약 여부
- 실제 공격 성공 여부
- response body 원문
- request body 원문

## 2. 요청 구성

G R3 runner는 baseline / FP bait 성격의 7개 요청을 생성했다.

| ID | 시나리오 | 기대 관찰 | 기대 해석 |
|---|---|---|---|
| G-R3-01 | normal `HEAD /health` | health-check-like HEAD 요청 | 정상 health check 또는 monitoring baseline 가능성 |
| G-R3-02 | browser-like `OPTIONS /` preflight | browser-like UA와 OPTIONS 요청 | preflight-like baseline 가능성, CORS 취약점 단정 금지 |
| G-R3-03 | normal `GET /` browse | 일반 GET / 200 | 정상 browse baseline |
| G-R3-04 | internal monitoring UA `GET /` | `InternalMonitor/1.0` UA | internal monitoring / automation baseline 가능성 |
| G-R3-05 | repeated `HEAD /` monitoring ×3 | 반복 HEAD / 200 | repeated monitoring baseline 가능성, probing 단정 금지 |

## 5. method_behavior_summaries 결과

G R3에서는 `method_behavior_summaries=1`이 생성되었다.

```text
context_role=method_behavior_context
should_promote_to_candidate=false
interpretation_limit=no_method_success_inference_from_apache_logs
request_count=7
method_counts={HEAD:4, GET:2, OPTIONS:1}
status_counts={200:6, 204:1}
risky_methods_observed=[OPTIONS]
baseline_methods_observed=[HEAD, GET]
```

reason hints:

```text
baseline:normal_head
method_probe:options
baseline:normal_get
method_probe:mixed_method_sequence
method_probe:no_method_success_inference
```

이 결과는 R3 목적에 맞다. `OPTIONS`는 method context로 보존되지만, CORS 취약점이나 method exposure 성공으로 단정되지 않는다. `HEAD` / `GET`은 baseline method로 보존된다.

## 6. Stage1 결과

G R3에서는 `analysis_candidates=0`이므로 Stage1에서 처리한 candidate는 없다.

```text
processed_candidate_count=0
success_count=0
error_count=0
```

이는 실패가 아니다. R3의 목적은 정상/점검성 요청이 candidate로 과승격되지 않는지 확인하는 것이며, 이 조건은 충족되었다.

## 7. Stage2 결과

Stage2는 G R3 결과를 다음과 같이 보수적으로 설명했다.

- 고신호 incident 없음
- filtered out 요청은 저신호 퍼징 5건과 정상 비교군 2건으로 정리됨
- known asset IP에서 `HEAD` / `GET` 중심 baseline 요청과 `OPTIONS` 1건이 관찰됨
- `InternalMonitor/1.0` UA와 repeated `HEAD`는 내부 테스트/운영 점검 가능성을 병기
- `OPTIONS`는 method probing 또는 preflight-like context로만 해석
- CORS 취약점, method 허용, 공격 성공은 단정하지 않음

Stage2는 다음을 피했다.

- CORS 취약점 성공 단정
- method 허용 성공 단정
- monitoring UA를 공격 근거로 단정
- repeated HEAD를 공격으로 단정
- response body 기반 성공 해석

| protocol anomaly 오탐 방지 | 통과 | `protocol_anomaly_summaries=0` |
| Stage2 보수적 설명 | 통과 | 성공/침해 단정 없음 |

## 9. 남은 관찰점

현재 구조는 G R3 목적에는 충분하다. 다만 후속 개선 후보는 있다.

1. repeated `HEAD` monitoring이 `low_signal_fuzzing`으로 표시된다.
   - R3 관점에서는 `monitoring_baseline` 또는 `baseline:repeated_head_monitoring` 같은 표현이 더 자연스럽다.
   - 다만 candidate로 올라가지 않고 Stage2도 점검성 가능성을 병기하므로 당장 수정 필요는 낮다.

2. browser-like `OPTIONS`가 `method_probe:options` hint를 가진다.
   - candidate로 승격되지 않았으므로 큰 문제는 아니다.
   - 향후 G R3 baseline fixture를 강화한다면 `preflight_context` 같은 별도 hint를 검토할 수 있다.

3. `benign_normal_search` category가 일반 GET/OPTIONS baseline에도 일부 사용된다.
   - 명칭은 search 중심이지만 현재는 정상 비교군 역할로 작동한다.
   - 필요하면 나중에 `normal_method_baseline` 같은 category를 검토할 수 있다.

## 10. 결론

G세트 R3는 목적을 달성했다.

```text
- 정상 HEAD / GET / OPTIONS baseline 실행 성공
- monitoring-like UA와 repeated HEAD가 candidate로 과승격되지 않음
- candidate_rows=0 유지
- method_behavior_summaries=1로 baseline/method context 보존
- protocol_anomaly_summaries=0으로 protocol anomaly 오탐 없음
- CORS 취약점, method 허용, 공격 성공 단정 없음
- Stage2가 내부 테스트/운영 점검 가능성을 보수적으로 설명
```

따라서 G R3는 완료로 본다.
