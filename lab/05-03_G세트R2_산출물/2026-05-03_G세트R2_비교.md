# 2026-05-03 G세트 R2 비교

## 1. 실험 개요

- 세트: G세트 HTTP Method / Protocol Anomaly
- 라운드: R2 — protocol / malformed request 관찰
- 실행 방식: Python raw socket runner
- runner: `lab/g_set/run_g_r2_protocol_anomaly.py`
- 분석 대상 raw: `lab/05-03_G세트R2_산출물/data/raw/all_2026-05-03_G_R2_kst.json`
- Stage2 결과: `openai-g_r2_protocol_anomaly_stage2_report.md`

G R2의 목적은 malformed/protocol-like 요청이 Apache `security`, `access`, `error` 로그 표면 중 어디에 남는지 확인하고, 이를 성공 단정 없이 protocol anomaly context로 보존할 수 있는지 검증하는 것이다.

이 실험은 다음을 확인하지 않는다.

- protocol bypass 성공 여부
- malformed request 우회 성공 여부
- 서버 침해 성공 여부
- virtual host bypass 성공 여부
- response body 원문
- request body 원문
- 서버 내부 설정 원문

---

## 2. 요청 구성

G R2 runner는 아래 6개 시나리오를 raw socket 기반으로 생성했다.

| ID | 시나리오 | 기대 관찰 | 해석 제한 |
|---|---|---|---|
| G-R2-01 | invalid method token (`FAKEMETHOD`) | unsupported/invalid method가 어떻게 기록되는지 확인 | method 우회 성공 단정 금지 |
| G-R2-02 | HTTP/1.0 odd request | `HTTP/1.0` 요청이 어떻게 기록되는지 확인 | 취약점 단정 금지 |
| G-R2-03 | bad protocol version | bad protocol이 어떤 status/log surface로 남는지 확인 | protocol bypass 성공 단정 금지 |
| G-R2-04 | missing Host | Host 없는 HTTP/1.1 요청이 어떻게 남는지 확인 | virtual-host 우회 성공 단정 금지 |
| G-R2-05 | odd Host | 이상 Host 값이 어떻게 남는지 확인 | Host header bypass 성공 단정 금지 |
| G-R2-06 | long path | 긴 path가 어떤 status/log surface로 남는지 확인 | exploit 성공 단정 금지 |

## 3. raw export 결과

`all` export 결과는 다음과 같다.

```text
total_count=12
access=6
security=6
error=0
```

즉, G R2 요청은 Apache `access`와 `security` 양쪽에 남았고, 이번 실행에서는 `error` 로그 row는 생성되지 않았다.

prepare 단계는 기존 정책에 따라 `security` 중심으로 분석했다.

```text
selected_source_tables=[security]
selected_source_rows=6
```

## 4. 최초 prepare 결과와 문제점

초기 prepare 결과에서는 G R2 요청이 완전히 사라지지는 않았지만, protocol/malformed 문맥이 충분히 보존되지 않았다.

초기 상태 요약:

```text
candidate_rows=0
supporting_events=0
filtered_out_rows=6
ip_behavior_aggregates=1
protocol_anomaly_summaries 없음
```

filtered row의 해석은 대략 다음처럼 정리되었다.

```text
FAKEMETHOD -> method_probe:unsupported_method
HTTP/1.0 -> baseline:normal_get
bad protocol -> baseline:normal_get
missing host -> baseline:normal_get
odd host -> baseline:normal_get
long path -> baseline:normal_get
```

이 상태는 G R2 목적에는 부족했다. 특히 `bad_protocol`, `missing_host`, `odd_host`, `long_path`는 정상 GET baseline이라기보다 protocol/malformed surface observation으로 보존되는 것이 더 적절하다.

## 5. 개선 후 prepare 결과

`protocol_anomaly_summaries`를 추가한 뒤 동일 raw를 다시 prepare 했다.

개선 후 요약:

```text
total_exported_rows=12
selected_source_rows=6
candidate_rows=0
distinct_incident_candidates=0
supporting_events=0
filtered_out_rows=6
ip_behavior_aggregates=1
method_behavior_summaries=1
protocol_anomaly_summaries=1
```

개별 row는 여전히 incident candidate로 승격되지 않았다. 대신 G R2의 핵심 문맥이 `protocol_anomaly_summaries` 1건으로 보존되었다.

summary의 주요 내용은 다음과 같다.

```text
context_role=protocol_anomaly_context
should_promote_to_candidate=false
interpretation_limit=protocol_anomaly_context_only_no_success_inference
request_count=6
status_counts={200:3, 400:3}
method_counts={GET:5, FAKEMETHOD:1}
```

관찰된 anomaly type:

```text
unsupported_method
http10_request
bad_protocol_version
missing_host
odd_host
long_path
```

reason hints:

```text
method_probe:unsupported_method
protocol_anomaly:unsupported_method
protocol_anomaly:malformed_request
protocol_anomaly:http10_request
protocol_anomaly:legacy_protocol_observation
protocol_anomaly:bad_protocol_version
protocol_anomaly:missing_host
protocol_anomaly:odd_host
protocol_anomaly:long_path
protocol_anomaly:no_success_inference
```

## 6. Stage1 결과

G R2에서는 `analysis_candidates=0`이므로 Stage1에서 처리한 candidate는 없다.

```text
processed_candidate_count=0
success_count=0
error_count=0
```

이는 실패가 아니다. G R2는 개별 malformed/protocol 요청을 고신호 incident로 올리는 대신, `protocol_anomaly_summaries`와 `method_behavior_summaries`로 context-only 보존하는 것을 목표로 한다.

---

## 7. Stage2 결과

Stage2는 protocol anomaly context를 적절히 설명했다.

주요 해석:

- 후보로 승격된 개별 침해 incident는 없음
- known asset IP에서 짧은 시간 안에 protocol/malformed 성격의 저신호 요청이 관찰됨
- `FAKEMETHOD`, `HTTP/1.0`, bad protocol version, missing/odd Host, long path 정황이 함께 보존됨
- status가 `200`과 `400`으로 혼재했지만 우회 성공이나 침해 성공으로 단정하지 않음
- 내부 테스트, 자동화 점검, 자체 호출 가능성을 병기

Stage2는 다음을 명시적으로 피했다.

- protocol bypass 성공 단정
- malformed request로 인한 우회 성공 단정
- Host header bypass 성공 단정
- 서버 침해 성공 단정
- response body 또는 request body 기반 해석

## 8. 체크포인트 평가

| 체크포인트 | 평가 | 비고 |
|---|---:|---|
| invalid method 보존 | 통과 | `protocol_anomaly:unsupported_method` |
| HTTP/1.0 관찰 보존 | 통과 | `protocol_anomaly:http10_request`, `legacy_protocol_observation` |
| bad protocol 보존 | 통과 | `protocol_anomaly:bad_protocol_version` |
| missing Host 보존 | 통과 | `protocol_anomaly:missing_host`, `malformed_request` |
| odd Host 보존 | 통과 | `protocol_anomaly:odd_host` |
| long path 보존 | 통과 | `protocol_anomaly:long_path` |
| candidate 과승격 방지 | 통과 | `candidate_rows=0` 유지 |
| context-only 원칙 | 통과 | `should_promote_to_candidate=false` |
| Stage2 protocol anomaly 설명 | 통과 | protocol anomaly context 섹션 생성 |
| 성공/침해/우회 단정 금지 | 통과 | 보수적 문구 유지 |

## 9. 남은 관찰점

현재 구조는 G R2 목적에는 충분하다. 다만 후속 개선 후보는 남아 있다.

1. `filtered_out_breakdown`은 여전히 `low_signal_fuzzing=6`으로 남는다.
   - 현재는 `protocol_anomaly_summaries`가 별도 context를 제공하므로 큰 문제는 아니다.
   - 필요하면 나중에 `protocol_anomaly_context` 또는 `protocol_low_signal_context` 같은 category를 검토할 수 있다.

2. `method_behavior_summaries`도 함께 생성된다.
   - G R2에서는 `method_behavior_summaries`보다 `protocol_anomaly_summaries`가 핵심이다.
   - Stage2는 이를 어느 정도 구분해 설명하고 있으므로 당장 수정은 필요 없다.

3. `access`와 `security`가 모두 export되었지만 prepare는 `security` 중심으로 사용했다.
   - 이번 결과에서는 `security`만으로도 필요한 문맥이 보존되었다.
   - 향후 malformed request가 `error`에만 남는 케이스가 나오면 prepare 입력/상관 방식 재검토가 필요하다.

## 10. 결론

G세트 R2는 목적을 달성했다.

```text
- raw socket 기반 protocol/malformed request 실행 성공
- access=6, security=6, error=0 확인
- 초기 prepare의 baseline:normal_get 뭉개짐 문제 확인
- 개선 후 protocol_anomaly_summaries=1 생성
- unsupported_method / http10_request / bad_protocol_version / missing_host / odd_host / long_path 보존
- candidate 과승격 없이 context-only 보존
- protocol bypass / malformed request 우회 / 서버 침해 성공 단정 없음
- Stage2가 protocol anomaly context를 보수적으로 설명
```

따라서 G R2는 완료로 본다.
