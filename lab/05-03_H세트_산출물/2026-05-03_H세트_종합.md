# 2026-05-03 H세트 종합 비교

## 1. 문서 목적

이 문서는 H세트 Static / Crawler / Scanner-like Noise 실험의 R1/R2/R3/R4 결과를 종합한다.

H세트의 목적은 실제 운영 로그에서 자주 보이는 정상/저신호 웹 요청을 공격으로 과승격하지 않고, Apache 로그 표면에 근거해 baseline/context/noise로 분리할 수 있는지 확인하는 것이다.

핵심 질문은 다음이다.

```text
1. static asset / health / normal browse 요청이 공격 candidate로 과승격되지 않는가?
2. crawler-like User-Agent와 robots/sitemap/product/category 접근을 실제 crawler 또는 공격으로 단정하지 않는가?
3. scanner-like sensitive path 접근을 파일 노출/애플리케이션 존재/침해 성공으로 단정하지 않는가?
4. 정상 baseline과 scanner-like path가 같은 window에 섞여도 단일 공격 성공으로 과장하지 않는가?
5. Stage2가 정상/저신호/민감 경로 문맥을 보수적으로 설명하는가?
```

H세트는 새 공격 성공을 증명하는 실험이 아니다. false positive를 줄이고 baseline/noise 해석을 안정화하는 데 초점이 있다.

---

## 2. 전체 결론

H세트 R1/R2/R3/R4는 전체적으로 목적을 달성했다.

```text
H R1: static / health / normal browse 요청을 static_baseline_summaries로 context-only 보존
H R2: crawler-like UA와 robots/sitemap/product/category 접근을 crawler_baseline_summaries로 context-only 보존
H R3: scanner-like sensitive path를 sensitive_path_probe_summaries로 context-only 보존하고 대표 /server-status 403만 low candidate로 유지
H R4: static/crawler/sensitive path가 섞인 상황을 mixed_baseline_scanner_summaries로 context-only 보존
```

가장 중요한 결과는 다음이다.

```text
- H R1/R2에서는 candidate_rows=0이 유지되었다.
- H R3/R4에서는 /server-status 403 대표 candidate 1건만 low severity로 남았다.
- static/crawler/sensitive path 관련 성공 단정은 발생하지 않았다.
- Stage2는 known asset, 내부 테스트, 운영 점검 가능성을 병기했다.
- 혼합 시나리오에서도 정상 baseline과 scanner-like context를 하나의 성공 공격으로 합치지 않았다.
```

## 4. H R1 요약 — Static / health baseline

### 4.1 목적

H R1은 favicon, robots.txt, sitemap.xml, JS/CSS/image asset, health endpoint, normal GET 요청이 공격 candidate로 과승격되지 않는지 확인했다.

### 4.2 관찰된 요청

```text
/favicon.ico
/robots.txt
/sitemap.xml
/assets/app.js
/assets/style.css
/images/logo.png
/api/health
/
```

### 4.3 개선 전 문제

초기 prepare에서는 이 요청들이 candidate로 올라가지는 않았지만, 모든 filtered row가 `dir_probe:burst`로만 남았다.

```text
candidate_rows=0
filtered_out_rows=8
static_baseline_summaries 없음
filtered row reason_hints=dir_probe:burst
```

이는 H세트의 static/health/browse baseline 문맥을 충분히 전달하지 못했다.

### 4.4 개선 후 결과

`static_baseline_summaries`를 추가한 뒤 다음처럼 정리되었다.

```text
candidate_rows=0
filtered_out_rows=8
static_baseline_summaries=1
ip_behavior_aggregates=1
```

summary 핵심:

```text
context_role=static_baseline_context
should_promote_to_candidate=false
interpretation_limit=static_content_not_visible_no_attack_inference
asset_categories_observed=[favicon, robots_txt, sitemap_xml, javascript_asset, css_asset, image_asset, health_check, normal_get]
```

### 4.5 판단

H R1은 성공이다.

```text
- static / health / normal browse 요청이 candidate로 과승격되지 않음
- static_baseline_summaries=1 생성
- static file 존재, robots/sitemap 내용, JS 실행, file exposure, health 정상 여부 단정 없음
- Stage2가 known asset 기반 내부 테스트/운영 점검 가능성을 병기
```

상세 문서:


## 5. H R2 요약 — Crawler-like baseline

### 5.1 목적

H R2는 Googlebot-like / GenericCrawler-like User-Agent, robots/sitemap, product/category browse 요청이 실제 crawler 또는 공격으로 과승격되지 않는지 확인했다.

### 5.2 관찰된 요청

```text
Googlebot-like /robots.txt
Googlebot-like /sitemap.xml
GenericCrawler /products/
GenericCrawler /category/
Browser-like GET /
GenericCrawler repeated /robots.txt, /sitemap.xml, /products/
```

### 5.3 개선 전 문제

초기 prepare에서는 candidate로 과승격되지는 않았지만, GenericCrawler의 `/products/`, `/category/`가 `dir_probe:burst` 중심으로 남았다.

```text
candidate_rows=0
filtered_out_rows=8
crawler_baseline_summaries 없음
/products/, /category/ -> dir_probe:burst
```

### 5.4 개선 후 결과

`crawler_baseline_summaries`를 추가한 뒤 다음처럼 정리되었다.

```text
candidate_rows=0
filtered_out_rows=8
static_baseline_summaries=1
crawler_baseline_summaries=1
ip_behavior_aggregates=1
```

summary 핵심:

```text
context_role=crawler_baseline_context
should_promote_to_candidate=false
interpretation_limit=crawler_ua_spoofable_no_content_or_page_existence_inference
crawler_like_user_agent_families=[googlebot_like, generic_crawler]
path_categories_observed=[robots_txt, sitemap_xml, product_browse, category_browse, normal_get]
```

### 5.5 판단

H R2는 성공이다.

```text
- Googlebot-like / GenericCrawler-like 요청이 candidate로 과승격되지 않음
- crawler_baseline_summaries=1 생성
- Googlebot-like UA를 실제 Googlebot으로 단정하지 않음
- robots/sitemap 내용, site structure, product/category page existence, 공격 성공 단정 없음
- Stage2가 crawler-like baseline 또는 low-signal crawl context로 보수적으로 설명
```

## 6. H R3 요약 — Scanner-like low-signal path

### 6.1 목적

H R3는 `/wp-login.php`, `/wp-admin/`, `/.env`, `/phpinfo.php`, `/server-status`, `/backup.zip` 같은 scanner-like sensitive path 요청을 파일 노출/애플리케이션 존재/침해 성공으로 단정하지 않고 context로 보존할 수 있는지 확인했다.

### 6.2 관찰된 요청

```text
/wp-login.php
/wp-admin/
/.env
/phpinfo.php
/server-status
/backup.zip
```

### 6.3 개선 전 문제

초기 prepare 결과는 다음과 같았다.

```text
candidate_rows=2
supporting_events=0
filtered_out_rows=7
probing_sequence_summaries=1
ip_behavior_aggregates=1
sensitive_path_probe_summaries 없음
```

특히 `/server-status` 403 두 건이 개별 analysis candidate로 남았고, 나머지 sensitive-looking path는 `dir_probe:*` 중심으로 정리되었다.

### 6.4 개선 후 결과

`sensitive_path_probe_summaries`를 추가한 뒤 다음처럼 정리되었다.

```text
candidate_rows=1
distinct_incident_candidates=1
supporting_events=1
filtered_out_rows=7
probing_sequence_summaries=1
ip_behavior_aggregates=1
sensitive_path_probe_summaries=1
```

대표 candidate:

```text
GET /server-status -> 403
verdict=suspicious_scan
severity=low
```

### 6.5 판단

H R3는 성공이다.

```text
- /server-status 대표 candidate 1건만 low severity로 유지
- 나머지 /server-status는 supporting context로 보존
- wp-login/wp-admin/.env/phpinfo/backup path는 filtered context로 보존
- sensitive_path_probe_summaries=1 생성
- WordPress 존재, admin access, 파일 노출, phpinfo 노출, server-status 노출/차단, backup 노출, 공격 성공 단정 없음
- Stage2가 suspicious_scan low로 보수적으로 설명
```


## 7. H R4 요약 — Mixed benign + scanner-like

### 7.1 목적

H R4는 정상 browse/static/crawler-like 요청과 scanner-like sensitive path가 같은 시간대에 섞였을 때, pipeline이 이를 하나의 공격으로 과도하게 묶지 않고 baseline context와 scanner context를 분리하는지 확인했다.

### 7.2 관찰된 요청

```text
GET /
GET /assets/app.js
GET /favicon.ico
GET /robots.txt
GET /sitemap.xml
GET /products/
GET /.env
GET /wp-login.php
GET /backup.zip
GET /server-status
```

### 7.3 개선 전 관찰

H R4 최초 prepare에서는 row-level hint는 어느 정도 분리됐지만, top-level mixed context가 명확하지 않았다.

```text
candidate_rows=1
filtered_out_rows=12
noise_summary_aggregates=3
ip_behavior_aggregates=1
mixed_baseline_scanner_summaries 없음
```

즉, 정상/static/crawler-like 요청과 scanner-like sensitive path가 같은 window에 섞였다는 것을 Stage2가 구조적으로 분리해 설명하기에는 부족했다.

### 7.4 개선 후 결과

`mixed_baseline_scanner_summaries`를 추가한 뒤 다음처럼 정리되었다.

```text
candidate_rows=1
filtered_out_rows=21
noise_group_count=3
static_baseline_summaries=1
crawler_baseline_summaries=1
sensitive_path_probe_summaries=1
mixed_baseline_scanner_summaries=1
ip_behavior_aggregates=1
```

summary 핵심:

```text
context_role=mixed_baseline_scanner_context
should_promote_to_candidate=false
baseline_contexts_observed=[normal_get, static_baseline, crawler_baseline]
scanner_contexts_observed=[sensitive_path_probe]
interpretation_limit=mixed_context_no_success_or_single_attack_inference
```

### 7.5 Stage2 결과

Stage2는 다음을 보수적으로 설명했다.

```text
- 대표 candidate는 /server-status 403 한 건
- static/crawler-like baseline과 sensitive path probe가 같은 window에 함께 관찰됨
- 이를 단일 공격 성공으로 확정하지 않음
- .env, backup.zip, wp-login.php의 성공/노출/존재를 단정하지 않음
- known asset 기반 내부 테스트/운영 점검 가능성 병기
```

다만 key finding severity가 `medium`으로 표현된 부분은 실제 top incident `low`보다 높아 표현 일관성 개선 후보로 남겼다.

### 7.6 판단

H R4는 성공이다.

```text
- mixed baseline + scanner-like 요청 실행 성공
- static/crawler/sensitive/mixed context가 모두 생성됨
- candidate는 /server-status 403 1건만 low severity로 유지
- 정상 baseline과 scanner-like context가 하나의 공격 성공으로 합쳐지지 않음
- 파일 노출, crawler 진위, page existence, WordPress 존재, attack success 단정 없음
```


## 11. 남은 개선 후보

현재 H세트 결과는 충분히 안정적이다. 다만 다음 표현 개선 후보가 남아 있다.

### 11.1 noise_category 세분화

현재 일부 row는 여전히 `low_signal_fuzzing` 또는 `low_signal_dir_probe`로 남는다.

표현 후보:

```text
static_asset_baseline
crawler_like_baseline
crawler_like_browse_context
sensitive_path_probe_context
health_check_error_context
mixed_baseline_scanner_context
```

현재는 top-level summary가 문맥을 보존하므로 급한 문제는 아니다.

### 11.2 Stage2 key finding severity 정합성

H R4에서 key finding severity가 대표 incident severity보다 높게 표현된 사례가 있었다.

```text
key finding: medium
representative incident: low
```

이는 탐지 실패는 아니지만 보고서 일관성 문제다. 이미 Stage2 guidance에 severity ceiling 원칙을 보강했다.

### 11.3 H R4 추가 반복 여부

H R4는 선택 실험이었고 현재 결과는 목적을 달성했다. 추가 반복은 필수는 아니다.
