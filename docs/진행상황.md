# 진행상황 정리본

- 문서 목적: 현재까지의 구축·코드 수정·비교 실험 진행 상황을 한 문서에서 파악할 수 있도록 정리한다.
- 기준 시점: 2026-04-30 E세트 R2B/R3B 정리 후
- 범위: Juice Shop 및 OpenCart 기반 Apache 로그 분석 파이프라인, A~E 비교 실험, 최근 코드 개선 방향, 다음 우선순위

---

## 1. 현재 목표

현재 프로젝트의 목표는 **Apache 웹 로그 기반 LLM 침입 로그 분석 파이프라인**을 구축하고, 여러 웹 애플리케이션 환경에서 일반화 가능한 탐지·해석 기준을 검증하는 것이다.

전체 흐름은 다음과 같다.

```text
Apache 로그 생성
  ↓
apache_log_shipper.py
  ↓
MariaDB(web_logs)
  ↓
export_db_logs_cli.py
  ↓
prepare_llm_input.py
  ↓
llm_stage1_classifier.py
  ↓
llm_stage2_reporter.py
```

핵심 원칙은 다음이다.

- Apache `security` 로그를 중심으로 공격 후보를 선별한다.
- LLM은 raw 전체가 아니라 전처리된 candidate와 context-only 정보를 본다.
- Juice Shop에만 맞추지 않고 OpenCart/PHP 환경에서도 일반화되는지 검증한다.
- `status_code=200`, `text/html`, `response_body_bytes`만으로 성공/유출/실행을 단정하지 않는다.
- 새 payload를 무작정 늘리기보다, 기존 실험에서 확인된 약점과 빈칸을 기준으로 보강한다.

## 2. 시스템 및 시간 정책

### 2.1 서버 역할

- 웹서버
  - Apache 로그 생성
  - `/opt/apache_log_shipper.py` 실행
  - `/opt/shipper.env`로 DB 접속 정보 관리
- DB 서버
  - MariaDB `web_logs` 저장
  - `apache_access_logs`, `apache_security_logs`, `apache_error_logs` 관리
- LLM 서버
  - DB export
  - prepare
  - Stage1 분류
  - Stage2 보고서 생성

### 2.2 로그 시간 정책

현재 시간 정책은 다음으로 고정했다.

- DB `log_time`: UTC naive datetime 저장
- 사용자의 export 입력: KST 기준
- DB 조회: KST 입력을 UTC로 변환해 조회
- export JSON 출력: KST ISO-8601 문자열

OpenCart 환경에서 서버 timezone 차이 때문에 KST naive로 저장되는 문제가 있었고, 이를 위해 다음을 수정했다.

- `src/apache_log_shipper.py`
  - Apache log_time의 timezone offset을 읽어 UTC naive로 DB 저장
  - `parse_error_time()`에 `%{uc}t` 형식 대응 보강
- `src/export_db_logs_cli.py`
  - timezone suffix 입력 허용
  - KST 입력 / UTC 조회 / KST 출력 흐름 보강

### 2.3 운영 파일 기준

웹서버 쪽 운영 구조는 다음 기준으로 정리했다.

```text
/opt/shipper.env
/opt/apache_log_shipper.py
```

`/opt/config/llm.env`는 웹서버 shipper 실행과 무관하므로 문서에서 제외했다.

## 3. 완료한 코드 개선

### 3.1 URL/double decode 및 HTML entity decode

`prepare_llm_input.py`에서 raw query, raw request target, URL decode depth 1/2, HTML entity decode view를 분석에 반영했다.

효과:

- SQLi double encoding 탐지 개선
- XSS HTML entity payload 탐지 개선
- C세트와 E세트에서 `&#x3C;script&#x3E;...` 형태를 XSS로 복원 가능

### 3.2 SQLi/XSS false positive 완화

교육용 SQL/XSS 검색을 공격으로 과승격하지 않도록 완화했다.

예시:

```text
how to use UNION in SQL
SELECT * FROM users tutorial
tutorial for onerror event handler
```

강한 공격 구조가 없으면 `possible_false_positive_*`, `false_positive_review_candidates`, 또는 context-only 후보로 낮춘다.

### 3.3 context-only 구조 보강

후보 밖 저신호 요청을 완전히 버리지 않고 Stage2 문맥으로 제공하기 위해 다음 구조를 도입했다.

- `supporting_events`
- `false_positive_review_candidates`
- `probing_sequence_summaries`

원칙:

- 개별 incident로 과승격하지 않는다.
- 같은 IP/시간대/endpoint family 기준으로 보조 맥락만 제공한다.
- Stage2는 이를 공격 성공 근거가 아니라 context-only로 해석한다.

### 3.4 PHP file disclosure 탐지 보강

E세트 R2에서 `path=php://filter...config.php`가 candidate에서 빠지는 문제가 있어 PHP/file disclosure hint를 보강했다.

일반 탐지 신호:

- `php://filter`
- `convert.base64-encode`
- `resource=`
- `config.php`
- `admin/config.php`
- `index.php`

효과:

- `route=php://filter...index.php` 유지 및 score 상승
- `path=php://filter...config.php` 신규 candidate 승격
- `/config.php`, `/admin/config.php` 직접 접근은 context-only 유지
- E세트 R2B에서 `file=`, `path=`, `route=` wrapper variant 모두 candidate 보존

### 3.5 정상 search baseline 분리

E세트 R3B에서 정상 `search=apple` 요청이 candidate로 과승격되지는 않았지만, 기존에는 `low_signal_fuzzing` 및 `temporal_context`로 표현되어 후보 밖 탐색성 요청처럼 보이는 문제가 있었다.

개선 후:

- 정상 검색은 `benign_normal_search`로 분리
- 근접 공격 candidate가 있는 경우 `supporting_role=reference_baseline`으로 보존
- `supporting_reason=nearby_normal_search_baseline`
- 단순 route encoding인 `%2F`는 공격성 `encoded_payload_trace`에서 제외

효과:

- 정상 검색 baseline이 공격 후보와 비교되는 reference baseline으로 표현됨
- SQLi/XSS candidate는 그대로 유지

남은 TODO:

- `benign_normal_search` row에 `dir_probe:burst` hint가 남는 경우가 있어, 정상 baseline row에서는 `dir_probe:*` 계열 hint를 제거하거나 `normal_search_baseline` 계열 hint로 교체하는 정리가 필요하다.

## 4. 비교 실험 진행 상황

### 4.1 A세트

- 기본 공격 로그 분석 흐름 검증
- OpenAI / Anthropic 보고서 비교 기준 마련
- 이후 B/C/D/E 세트 문서 구조의 기준 역할

### 4.2 B세트 SQLi / Boolean / Time-based

주요 결과:

- GET SQLi 가시성 확인
- POST body visibility 한계 확인
- Boolean Blind에서 `x')) OR 1=1 --`와 `x')) AND 1=2 --`의 `response_body_bytes` 차이 확인
- Time-based randomblob delay는 기대한 수준으로 발생하지 않아 실패로 명시
- double encoding, temporal chain, educational SQL FP 완화 검증

### 4.3 C세트 XSS

주요 결과:

- 기본 `<script>` payload 탐지 성공
- URL encoded / HTML entity encoded XSS 탐지 성공
- `onerror`, `javascript:`, `document.cookie`, external exfil intent hint 보강
- 교육용 XSS 검색은 candidate 과승격을 줄이고 review context로 보존

### 4.4 D세트 Traversal / HPP / Directory Probing

주요 결과:

- R1 Path Traversal: `../`, `%2e%2e%2f`, null byte 계열 시도 탐지 성공
- R2 HPP: HPP+SQLi / HPP+XSS 탐지 성공, benign duplicate HPP는 context로 보존
- R3 Directory Probing: 단발 directory probe를 candidate로 과승격하지 않고 sequence summary로 보존

### 4.5 E세트 OpenCart

E세트는 Juice Shop이 아닌 OpenCart/PHP 환경에서 탐지 로직이 일반화되는지 확인하기 위한 세트다.

#### R1 — route traversal / admin path

- `route=../../../../etc/passwd` 형태의 route parameter traversal intent 탐지 성공
- `/admin/`, `/admin/index.php`는 개별 incident로 과승격하지 않고 context-only probing sequence로 보존
- OpenCart의 `/admin/index.php`는 실제 관리자 로그인 페이지일 수 있어 Juice Shop SPA fallback과 다르게 해석해야 함

#### R2 — PHP wrapper / config exposure

- 수정 전에는 `path=php://filter...config.php`가 candidate에서 누락됨
- 코드 수정 후 `route=php://filter...index.php`, `path=php://filter...config.php` 모두 `suspicious_file_disclosure` hint로 candidate 보존
- `/config.php`, `/admin/config.php`는 200/0B 응답이지만 파일 노출 성공으로 단정하지 않고 context-only 유지

#### R2B — PHP wrapper variant 일반화

- `file=php://filter/convert.base64-encode/resource=config.php` candidate 보존
- `path=php://filter/convert.base64-encode/resource=admin/config.php` candidate 보존
- `route=php://filter/resource=config.php`는 base64 없이도 candidate 보존
- direct `/config.php`, `/admin/config.php`는 `low_signal_dir_probe`로 분리되어 과승격되지 않음
- OpenAI Stage2는 PHP wrapper 기반 파일 노출 시도 정황으로 설명하면서 실제 파일 내용 노출 성공은 단정하지 않음
- 남은 한계: Stage1 최종 verdict는 여전히 `suspicious_path_traversal`로 수렴하는 경향이 있음

#### R3 — product/search SQLi/XSS

- `search=x')) OR 1=1 --` SQLi candidate 탐지 성공
- `search=<script>alert(1)</script>` XSS candidate 탐지 성공
- `search=&#x3C;script&#x3E;alert(1)...` HTML entity XSS candidate 탐지 성공
- OpenCart의 `/index.php?route=product/search&search=...` 구조에서도 기존 탐지 로직이 동작함을 확인

#### R3B — 정상 search baseline / SQLi / XSS 분리

- 정상 `search=apple`은 candidate로 과승격되지 않음
- 정상 search는 `benign_normal_search` 및 `reference_baseline`으로 보존
- SQLi 1건과 XSS 2건은 모두 candidate로 유지
- OpenAI Stage2는 정상 baseline을 후보 밖 탐색성 요청이 아니라 정상 비교군으로 설명
- Anthropic은 크레딧 잔고 문제로 미실행
- 남은 TODO: `benign_normal_search` row에 남는 `dir_probe:burst` hint 정리

## 5. 현재 판단 기준

### 5.1 성공 단정 금지

Stage2 보고서의 핵심 원칙은 다음이다.

- `status_code=200`만으로 공격 성공을 단정하지 않는다.
- `resp_content_type=text/html`만으로 XSS 실행 성공을 단정하지 않는다.
- `response_body_bytes` 차이는 보조 지표이지 본문 노출 증거가 아니다.
- Apache 로그만으로 파일 내용, DB 결과, 브라우저 실행을 직접 확인할 수 없다.

### 5.2 일반화 우선

금지 방향:

- `lab-*` User-Agent 기반 탐지
- 특정 IP 기반 탐지
- 특정 response_body_bytes 값 hard-code
- Juice Shop/OpenCart 이름 기반 분기

허용 방향:

- 일반 URL encoding / double encoding
- 일반 SQLi/XSS/path traversal/PHP wrapper 신호
- Apache 로그 표면 지표 기반 해석

## 7. 다음 우선순위

현재는 payload를 더 늘리는 것보다, 코드 품질과 회귀 안정성을 먼저 잡는 편이 낫다.

### 7.1 1순위 — 회귀 fixture 정리

목적:

- 지금까지 추가한 개선이 서로 깨지지 않도록 자동 또는 반자동 점검 체계를 만든다.
- 실제 raw를 매번 수동으로 찾아 돌리는 방식에서 벗어난다.

권장 fixture 묶음:

- B세트 R2B: double decoded SQLi, educational SQL FP, supporting_events
- C세트: HTML entity XSS, XSS FP review
- D세트 R3: directory probing sequence summary
- E세트 R2/R2B: PHP wrapper candidate, direct config path context-only
- E세트 R3/R3B: OpenCart search SQLi/XSS, 정상 search baseline `benign_normal_search` / `reference_baseline`

### 7.2 2순위 — `suspicious_file_disclosure` verdict 정식화

목적:

- `php://filter`가 계속 `suspicious_path_traversal`로 흡수되는 문제 완화
- PHP wrapper/source disclosure 계열을 path traversal과 분리

검토 후보:

```text
suspicious_file_disclosure
suspicious_source_disclosure
suspicious_lfi
```

### 7.3 3순위 — 작은 hint 품질 개선

후속 개선 후보:

- benign normal search row에서 `dir_probe:*` hint 제거
- SQLi `xclose` / quote termination hint 추가
- direct config path `200/0B` context hint 세분화
- Stage2 `php://filter/convert.base64-encode` source disclosure 설명 보강
- known asset IP 실행 명령 정리

### 7.4 이후 확장 후보

새 세트를 만든다면 Apache 로그 표면에서 관찰 가능한 유형만 선택한다.

- F세트: Auth/Login abuse
  - login endpoint 반복, status 변화, content_length 변화, same src_ip burst
  - raw POST body가 없으므로 username/password와 성공/실패는 단정하지 않음
- G세트: HTTP method / protocol anomaly
  - OPTIONS, TRACE, PUT, DELETE, HEAD
  - method probing, reconnaissance, misconfiguration 가능성 정도로 제한

### 7.5 보류 또는 제한 유지

- Time-based SQLi: B세트 R2A에서 실패로 기록. DB/앱별 payload 재설계 전까지 보류
- POST body payload 분석: raw POST body가 Apache 로그에 없으므로 성공/실패 판단 확장 금지
- response body 원문 기반 성공 판정: 현재 구조에서는 하지 않음
- 특정 실험환경 전용 규칙: `lab-*` UA, 특정 IP, 특정 response size hard-code 금지

## 8. 현재 리스크

### 8.1 Stage1 verdict taxonomy 한계

- `php://filter` → `suspicious_path_traversal`로 표현되는 경향
- file disclosure/source disclosure 전용 verdict 부족

### 8.2 LLM provider별 서술 차이

OpenAI는 대체로 보수적으로 성공 단정을 피한다. Anthropic은 위험도와 임팩트를 더 적극적으로 설명한다. 최종 문서에서는 Anthropic의 강한 표현을 Apache 로그 표면 기준으로 제한해 해석해야 한다.

### 8.3 실험환경과 일반환경의 차이

Juice Shop과 OpenCart는 통제된 실험 환경이다. 결과를 일반 서비스에 확대할 때는 Apache 로그 표면에서 관찰 가능한 신호로 제한해 설명해야 한다.

### 8.4 payload 확장으로 인한 결론 희석 위험

목적 없이 payload를 늘리면 보고서가 길어지고 핵심 결론이 흐려진다. payload 확장은 “새로운 약점 확인” 또는 “정상/공격 분리 확인” 목적이 있을 때만 진행한다.

## 9. 현재 상태 한 줄 요약

현재는 **Juice Shop과 OpenCart를 대상으로 A~E 비교 실험을 대부분 수행했고, 그 과정에서 URL/HTML entity decoding, supporting context, probing summary, PHP file disclosure 탐지, UTC/KST 시간 정책, 정상 search baseline 분리를 보강한 상태**다. 다음 핵심 작업은 **추가 payload 확대보다 회귀 fixture 정리와 `suspicious_file_disclosure` verdict 정식화**다.
