# 진행상황

- 기준 시점: 2026-05-02
- 문서 역할: 현재 상태를 빠르게 확인하는 짧은 대시보드

## 현재 상태 요약

- Apache 웹 로그 기반 LLM 침입 로그 분석 파이프라인을 유지 중이다.
- 구조는 `export -> prepare -> stage1 -> stage2` 이다.
- 분석 근거는 Apache 로그 표면에 직접 남는 필드로 제한한다.
- raw POST body, response body 원문, DB 결과, 브라우저 실행 여부는 사용하지 않는다.
- `status_code=200`, `text/html`, `response_body_bytes`만으로 성공, 침해, 유출을 단정하지 않는다.

## 현재 지원 범위

- SQLi
- XSS
- traversal
- HPP
- PHP wrapper / file disclosure 시도
- Log4Shell-style JNDI lookup
- SSRF-like internal / metadata target
- SSTI expression
- webshell-like access pattern
- Auth/Login abuse context
- `supporting_events`
- `probing_sequence_summaries`
- `ip_behavior_aggregates` context-only 문맥
- `auth_behavior_summaries` context-only 문맥

## 최근 확인된 실험 상태

- A~E세트: SQLi, XSS, Traversal, HPP, PHP wrapper, OpenCart search/baseline 검증 완료
- F세트 R1: Auth/Login abuse prepare + Stage1/Stage2 구조 검증 완료
  - 반복 401 login candidate noise를 `auth_behavior_summaries` 중심으로 축소
  - candidate `43 -> 3`, supporting events `0 -> 40`
  - 200 login baseline은 `auth_baseline_context`로 분리
  - POST body 미확인 및 로그인 성공/계정 탈취 단정 금지 유지
- F세트 R2A: Python runner 기반 저속/혼합/FP baseline 검증 완료
  - `slow_brute`, `interleaved_browse`, `chrome_200`, `ci_200` 실행
  - candidate `3`, supporting events `6`, auth behavior summary `1`
  - Chrome/CI 200 login은 candidate로 과승격되지 않음
  - 저속 반복 auth 실패는 보존하되 rapid burst로 오판하지 않음

## 회귀 검증 상태

- prepare regression: 12 fixtures, `warn=0 fail=0`
- stage dry-run regression: 6 fixtures, `warn=0 fail=0`
- `run_analysis_pipeline.py --dry-run` 기반으로 실제 LLM API 호출 없이 Stage1/Stage2 구조 검증 가능
- `py_compile` 주요 스크립트 통과

## 주요 제한

- raw POST body 분석 불가
- response body 원문 없음
- DB query 결과 없음
- 브라우저 실행 검증 없음
- 로그인 성공, 계정 탈취, credential stuffing 성공은 Apache 로그만으로 단정하지 않음
- 성공, RCE, 유출, 침해를 status/bytes/content-type만으로 단정하지 않음
- 실험환경 특화 rule 금지
  - `lab-*` UA
  - 특정 IP
  - 특정 response size
  - 특정 제품명
  - 특정 route 예외 처리
