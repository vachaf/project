# A~H세트 중간정리

- 작성 기준일: 2026-05-03
- 문서 역할: A~H세트까지의 현재 성과, 한계, 다음 판단사항을 한 번에 확인하기 위한 중간정리
- 적용 범위: Apache 웹 로그 기반 LLM 침입 로그 분석 파이프라인

---

## 1. 현재 프로젝트 상태

현재 파이프라인은 Apache `security/access/error` 로그 표면 지표만으로 공격 정황과 정상/저신호 baseline을 보수적으로 정리하는 구조다.

```text
Apache logs
-> export_db_logs_cli.py
-> prepare_llm_input.py
-> llm_stage1_classifier.py
-> llm_stage2_reporter.py
```

핵심 전제는 다음이다.

```text
- response body 원문은 보지 않는다.
- raw POST body는 보지 않는다.
- DB 결과는 보지 않는다.
- 브라우저 실행 여부는 보지 않는다.
- status_code, content_type, response_body_bytes만으로 성공/침해/유출을 단정하지 않는다.
```

이 프로젝트는 성공한 공격을 확정하는 시스템이 아니라, Apache 로그 표면에서 관찰 가능한 공격 시도·문맥·정상 baseline을 LLM이 과장하지 않도록 구조화하는 분석 파이프라인이다.

## 2. 현재까지의 큰 성과

A~H세트 기준으로 다음 범위를 검증했다.

| 범위 | 현재 상태 |
|---|---|
| SQLi | GET SQLi, double encoding, xclose/quote termination hint 보존 |
| XSS | URL/HTML entity decode 기반 XSS 복원, tutorial/FP 억제 |
| Traversal/HPP/Dir Probe | probing sequence와 context-only 보존 |
| PHP wrapper/file disclosure | `php://filter` 계열을 `suspicious_file_disclosure`로 분리 |
| Auth/Login Abuse | 반복 401, 401/200 혼재, 저속/rapid auth 문맥 보존 |
| HTTP Method/Protocol | method behavior, protocol anomaly를 성공 단정 없이 context 보존 |
| Static/Crawler/Scanner-like Noise | static/crawler/sensitive/mixed baseline과 scanner-like low signal 분리 |
| Regression | prepare regression 18개, stage dry-run regression 12개로 고정 |
| Runner | F/G/H 세트 일부를 Python runner 기반으로 전환 |
| LLM 샘플 검증 | F/G/H 5개 샘플 수동 review, 46/50 = 92% |

## 3. 세트별 요약

### 3.1 A~E세트

A~E세트는 기존 핵심 공격군 검증에 해당한다.

```text
A: 기본 인증/흐름
B: SQLi / POST body visibility / evasion
C: XSS / encoding / FP
D: Traversal / HPP / directory probing
E: OpenCart / PHP wrapper / search baseline
```

주요 결론:

```text
- GET 기반 SQLi/XSS/traversal/HPP/PHP wrapper는 Apache 로그 표면에서 후보/문맥으로 보존 가능하다.
- Time-based SQLi는 duration/ttfb 차이가 부족해 보류 상태다.
- POST body payload는 기본 Apache 로그에 보이지 않으므로 성공/실패를 단정하지 않는다.
- PHP wrapper는 단순 traversal이 아니라 source/config disclosure 시도로 별도 설명하는 것이 적절하다.
```

---

### 3.2 F세트 — Auth/Login Abuse

F세트는 POST body가 보이지 않는 상태에서 auth endpoint 반복 패턴을 해석할 수 있는지 확인했다.

완료된 라운드:

```text
F R1: 반복 401 / rapid burst / 401-200 혼재
F R2A: 저속 반복 / browse 혼재 / Chrome·CI baseline
F R2B: existing/nonexistent/lockout-probe response delta 관찰
```

주요 개선:

```text
auth_behavior_summaries
supporting_events auth_behavior_support
auth_baseline_context
```

주요 결론:

```text
- 반복 401 요청을 개별 incident로 과다 나열하지 않고 대표 candidate + supporting context로 줄일 수 있었다.
- 200 login은 baseline/context로 분리할 수 있었다.
- POST body가 없으므로 로그인 성공, 계정 탈취, credential stuffing 성공, lockout 발동은 단정하지 않는다.
- F R2B에서 existing/nonexistent/lockout 의도 그룹은 Apache 표면상 모두 401/26B로 유사하게 관찰되어 계정 존재 여부나 lockout 발동을 단정할 수 없었다.
```

---

### 3.3 G세트 — HTTP Method / Protocol Anomaly

G세트는 method/protocol surface behavior를 보수적으로 해석할 수 있는지 확인했다.

완료된 라운드:

```text
G R1: OPTIONS/TRACE/PUT/DELETE/HEAD/GET method probing
G R2: raw socket 기반 malformed/protocol anomaly
G R3: HEAD/GET/OPTIONS/monitoring UA baseline
```

주요 개선:

```text
method_behavior_summaries
protocol_anomaly_summaries
```

주요 결론:

```text
- OPTIONS/TRACE/PUT/DELETE는 method behavior context로 보존 가능하다.
- HEAD/GET baseline은 candidate로 과승격되지 않았다.
- raw socket 기반 invalid method, bad protocol, missing/odd Host, long path는 protocol_anomaly_summaries로 보존 가능하다.
- PUT 업로드, DELETE 삭제, TRACE/XST, OPTIONS/CORS 취약점, protocol bypass 성공은 Apache 로그만으로 단정하지 않는다.
```

---

### 3.4 H세트 — Static / Crawler / Scanner-like Noise

H세트는 정상/저신호 웹 요청을 공격으로 과승격하지 않고 baseline/context/noise로 분리할 수 있는지 확인했다.

완료된 라운드:

```text
H R1: static / health / normal browse baseline
H R2: crawler-like baseline
H R3: scanner-like sensitive path
H R4: mixed benign + scanner-like
```

주요 개선:

```text
static_baseline_summaries
crawler_baseline_summaries
sensitive_path_probe_summaries
mixed_baseline_scanner_summaries
```

주요 결론:

```text
- favicon/robots/sitemap/static asset/health/normal GET은 candidate로 과승격되지 않았다.
- Googlebot-like/GenericCrawler-like UA는 실제 crawler로 단정하지 않고 crawler-like context로 보존했다.
- scanner-like sensitive path는 대표 /server-status candidate 1건과 sensitive_path_probe_summaries로 보존했다.
- mixed benign + scanner-like 요청은 mixed_baseline_scanner_summaries로 분리 보존했다.
- WordPress 존재, admin access, .env/phpinfo/server-status/backup 노출, page existence, site structure, crawler authenticity는 Apache 로그만으로 단정하지 않는다.
- 정상 baseline과 scanner-like path가 같은 window에 있어도 단일 공격 성공으로 합치지 않는다.
```

## 4. 현재 핵심 구조

현재 prepare 단계에서 보존하는 주요 context 구조는 다음과 같다.

| 구조 | 역할 |
|---|---|
| `analysis_candidates` | Stage1에 넘길 대표 후보 |
| `supporting_events` | 후보 밖 보조 문맥 |
| `false_positive_review_candidates` | 오탐/교육용 질의 검토 문맥 |
| `probing_sequence_summaries` | directory/probing burst context |
| `ip_behavior_aggregates` | same src_ip/time window 행동 요약 |
| `auth_behavior_summaries` | 반복 auth endpoint 문맥 |
| `method_behavior_summaries` | HTTP method usage 문맥 |
| `protocol_anomaly_summaries` | malformed/protocol anomaly 문맥 |
| `static_baseline_summaries` | static/health/browse baseline 문맥 |
| `crawler_baseline_summaries` | crawler-like UA/browse baseline 문맥 |
| `sensitive_path_probe_summaries` | scanner-like sensitive path probing 문맥 |
| `mixed_baseline_scanner_summaries` | baseline/static/crawler-like와 sensitive path가 같은 window에 섞인 문맥 |

공통 원칙은 다음이다.

```text
*_summaries / *_aggregates 는 context-only 이며, 그 자체가 개별 incident 승격 근거가 아니다.
```


## 7. 지금까지의 설계 판단

### 7.1 좋았던 방향

```text
- 실험 먼저, 필요한 context summary를 나중에 추가하는 방식이 잘 작동했다.
- curl 나열보다 Python runner가 재현성과 기록성 측면에서 낫다.
- context-only summary를 추가하면 Stage2가 성공 단정을 줄이고 보수적으로 설명한다.
- representative candidate + supporting_events 방식은 반복 요청 noise를 줄이는 데 효과적이다.
- mixed summary는 정상 baseline과 scanner-like context가 섞인 운영형 시나리오를 설명하는 데 유용했다.
```

### 7.2 계속 유지할 방향

```text
- 새 실험 세트는 먼저 설계 문서 작성
- 그 다음 runner 작성
- 그 다음 prepare-only 확인
- 필요하면 context summary/hint 추가
- 그 다음 Stage1/Stage2 실행
- 마지막으로 비교 문서 작성
```

### 7.3 피해야 할 방향

```text
- 실험환경 특화 hard-code
- lab-* UA 기반 탐지
- 특정 IP 기반 탐지
- 특정 response size 기반 성공 판단
- status_code=200 기반 성공 단정
- response body/POST body/DB 결과가 있는 것처럼 해석
- context-only summary를 severity 상향의 단독 근거로 사용
```

## 8. 남은 개선 후보

### 8.1 noise_category 세분화

현재 일부 filtered row는 여전히 넓은 category를 사용한다.

후보:

```text
static_asset_baseline
crawler_like_baseline
crawler_like_browse_context
sensitive_path_probe_context
health_check_error_context
mixed_baseline_scanner_context
```

현재는 top-level summaries가 문맥을 보존하므로 급한 문제는 아니다.

검토 판단:

```text
즉시 구현보다는 보류가 적절하다.
H R4에서도 mixed_baseline_scanner_summaries가 문맥을 보존했으므로 category 세분화는 가독성 개선 후보에 가깝다.
운영 로그에서 low_signal_dir_probe / low_signal_fuzzing이 너무 넓게 보일 때 재검토한다.
```

### 8.2 Stage2 wording 표준화 추가

이미 다음을 문서화했다.

```text

```

## 10. 중간 결론

A~H세트 기준으로 파이프라인은 다음 능력을 갖춘 상태다.

```text
- 공격성 payload 구조를 후보로 보존한다.
- 반복/시퀀스/집계 문맥을 context-only로 보존한다.
- 정상/저신호 baseline을 별도 문맥으로 분리한다.
- mixed benign + scanner-like 상황에서도 단일 공격 성공으로 과장하지 않는다.
- LLM이 성공/침해/유출을 단정하지 않도록 policy와 report input을 제공한다.
- prepare/stage dry-run regression으로 핵심 동작을 고정한다.
```

아직 최종 발표용 정리는 아니지만, 현재 단계는 중간 점검 기준으로 충분히 의미 있는 안정화 지점이다.
