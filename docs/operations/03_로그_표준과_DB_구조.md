# 03_로그_표준과_DB_구조

- 문서 상태: 정리본
- 버전: v1.4
- 작성일: 2026-04-09
- 기준 코드:
  - `src/apache_log_shipper.py`
  - `src/export_db_logs_cli.py`
  - `src/prepare_llm_input.py`

## 1. 목적

Apache 로그와 MariaDB 저장 구조를 현재 코드 기준으로 정리한다.
실제 실행 명령은 [01_운영_기준_실행_가이드.md](./01_운영_기준_실행_가이드.md)를 우선한다.
이 문서는 prepare/stage1/stage2 분석 전략 문서가 아니라 로그 3종과 DB 구조 기준 문서다.

다만 downstream 분석에서 실제 사용하는 값 중 일부는 DB 원본 컬럼이 아니라 `prepare_llm_input.py` 단계에서 생성되는 산출 필드다. 이 문서에서는 DB 원본 저장 컬럼과 prepare 산출 필드를 구분해서 해석한다.

## 2. 전체 구조

```text
Apache
  ↓
access / security / error log
  ↓
apache_log_shipper.py
  ↓
MariaDB(web_logs)
  ↓
apache_access_logs
apache_security_logs
apache_error_logs
  ↓
export_db_logs_cli.py
  ↓
prepare_llm_input.py
  ↓
LLM 분석용 정제 산출물
```

## 3. 로그 역할

### 3.1 access log

- 운영 확인용
- 기본 요청 흐름과 기준선 비교용

현재 분석 파이프라인의 주 입력은 아니다.

### 3.2 security log

- 기본 prepare 입력
- 분석 기본 입력
- 요청 단위 메타데이터 저장
- `request_id` 기반 상관분석 중심

### 3.3 error log

- 예외/장애 확인용
- 5xx 또는 `request_id`/`error_link_id` 연계 확인용 보조 입력

## 4. 로그 파일명 표준

- `/var/log/apache2/app_access.log`
- `/var/log/apache2/app_security.log`
- `/var/log/apache2/app_error.log`

## 5. 식별자 기준

- 주 식별자: `request_id`
- 보조 식별자: `error_link_id`

현재 문서 기준으로 access 로그는 `request_id` 직접 매칭의 중심이 아니다. security/error 축이 상관분석의 기준이다.

## 6. DB 기본

- DB 이름: `web_logs`
- 문자셋: `utf8mb4`

최종 테이블:

- `apache_access_logs`
- `apache_security_logs`
- `apache_error_logs`

현재 분석 파이프라인에서 DB 원본값으로 특히 직접 쓰는 필드:

- `request_id`
- `error_link_id`
- `src_ip`
- `method`
- `uri`
- `query_string`
- `status_code`
- `duration_us`
- `ttfb_us`
- `resp_content_type`
- `response_body_bytes`
- `raw_request`
- `raw_log`
- `request_target` (v2 로그 포맷에서 제공될 때)

`apache_security_logs`에는 아래 과거 파생/비로그 컬럼을 두지 않는다.

- `host`  
  security log의 client-supplied Host header는 `req_host`로 통일한다. legacy v1 로그의 `host` key는 shipper가 `req_host`로 fallback 매핑한다.
- `attack_label`
- `risk_score`
- `matched_rule`
- `is_suspicious`

위 파생값은 Apache key=value 원본 로그 필드가 아니다. 필요하면 LLM pipeline 산출물 또는 별도 분석 테이블에서 관리한다.

### 7.3 `apache_error_logs`

- `id`

- `error_link_id`
- `request_id`
- `module_name`
- `log_level`
- `src_ip`
- `peer_ip`
- `message`
- `raw_log`
- `created_at`

## 8. `resp_html_*` 보류와 실제 사용 필드 구분

신규 `apache_security_logs` DDL에는 아래 `resp_html_*` 파생/비로그 컬럼을 두지 않는다.

- `resp_html_norm_fingerprint`
- `resp_html_fingerprint_version`
- `resp_html_baseline_name`
- `resp_html_baseline_match`
- `resp_html_baseline_confidence`
- `resp_html_features_json`

현재 기준:

- 과거 실험 DB나 문서에는 위 컬럼명이 남아 있을 수 있다.
- 하지만 현재 신규 DDL/shipper 기준에서는 원본 저장 컬럼으로 유지하지 않는다.
- 값 생성 로직은 보류 상태다.
- 현재 분석 파이프라인의 핵심 기준으로 사용하지 않는다.
- `resp_html_*` 값이 없다고 해서 파일 노출 성공/실패를 단정하지 않는다.
- 자세한 기준은 [99_HTML_fallback_fingerprint_구현_검토와_보류_결정.md](../design/99_HTML_fallback_fingerprint_구현_검토와_보류_결정.md)를 본다.

현재 유지해야 하는 실제 downstream 사용 필드:

DB 원본 저장 컬럼:

- `resp_content_type`
- `response_body_bytes`
- `raw_request`
- `raw_log`
- `request_target` (v2 로그 포맷에서 제공될 때)
- `uri`
- `query_string`

prepare 산출 필드:

- `raw_request_target`
- `path_normalized_from_raw_request`
- `likely_html_fallback_response`

주의:

- `raw_request_target`은 DB 원본 컬럼이 아니다. `prepare_llm_input.py`가 `raw_request`의 request line에서 method와 protocol 사이의 target을 추출해 만든다.
- `request_target`은 v2 security log format에서 DB에 저장될 수 있는 원본 관찰 컬럼이고, `raw_request_target`과 이름과 생성 위치가 다르다.
- `path_normalized_from_raw_request`와 `likely_html_fallback_response`는 `prepare_llm_input.py` 단계에서 `raw_request`, `uri`, `resp_content_type`, `response_body_bytes` 등을 바탕으로 계산되는 downstream 분석용 보조값이다.
- `likely_html_fallback_response=True`는 fallback-like 응답 관찰값일 뿐이며 파일 노출, traversal 성공, 침해 성공의 근거가 아니다.

## 9. 시간 처리

- DB 저장 기준: UTC
- 사용자 조회 기준: KST
- export 출력 기준: KST ISO-8601

이 기준은 `export_db_logs_cli.py` 와 문서 전체에서 동일하게 유지한다.

## 10. 운영 메모

- 기본 prepare/분석 입력은 `apache_security_logs`
- `apache_error_logs`는 5xx, 예외, `request_id`/`error_link_id` 상관분석 보조로 사용한다.
- `apache_access_logs`는 운영 확인과 기준선 비교 보조로 사용한다.
- 모든 테이블의 `raw_log`는 원문 대조용으로 중요하다.
- 신규 DB 구축 기준은 [02_MariaDB_환경_구축_및_설치.md](./02_MariaDB_환경_구축_및_설치.md)의 DDL을 우선한다.
