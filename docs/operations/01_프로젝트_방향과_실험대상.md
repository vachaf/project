## 1. 문서 목적

이 문서는 현재 진행 중인 프로젝트가 **무엇을 목표로 하는지**, 그리고 그 목표에 맞추어 **어떤 실험 대상을 어떤 역할로 유지하는지**를 정리하기 위한 상위 방향 문서이다.

기존에는 단순한 웹사이트 또는 쇼핑몰 구축 관점에서 실습 대상을 검토했으나, 프로젝트가 구체화되면서 목적이 달라졌다. 현재 프로젝트의 중심은 단순 서비스 구축이 아니라, 다음과 같은 보안 분석 실험 파이프라인에 있다.

- 정상 요청과 공격성 요청을 함께 발생시키는 것
- Apache access/security/error 로그를 체계적으로 수집하는 것
- 수집한 로그를 MariaDB에 저장하는 것
- 저장된 로그를 바탕으로 공격 징후 후보를 추출하고 분류하는 것
- LLM 또는 규칙 기반 분석기로 해석 가능한 입력과 보고서를 생성하는 것
- Web UI에서 분석 작업 상태와 결과를 확인하는 것

즉, 이 문서는 “어떤 웹 애플리케이션을 설치할 것인가”보다 먼저, **왜 그 애플리케이션과 topology가 필요한가**를 설명하는 방향 문서이다.

## 2. 프로젝트의 출발점과 방향 변화

초기 단계에서는 Ubuntu 22.04 환경에 Apache2, PHP, MySQL, OpenCart를 조합하여 **간단한 쇼핑몰 구축 실습**을 하는 방향을 검토하였다. 이 구성은 다음과 같은 학습 목표에는 적합하다.

- Ubuntu 서버 설치와 기본 운영 실습
- Apache 기반 웹서버 구축 실습
- 데이터베이스 연동 구조 이해
- 관리자 페이지와 상품 관리 기능 확인
- 기본 웹 로그 확인

하지만 프로젝트의 목적이 점차 구체화되면서, 단순한 쇼핑몰 설치보다 **공격 요청을 발생시키고 그 로그를 분석하는 실험**이 더 중요해졌다. 이 시점부터 실습 대상 선정 기준은 “서비스 구축이 쉬운가”보다 “공격 재현, 로그 수집, topology별 해석 한계 확인에 적합한가”로 바뀌었다.

따라서 현재 프로젝트는 일반적인 웹서비스 운영 실습이 아니라, **Apache logs-only 기반 웹 공격 관찰, 후보 추출, DB 저장, LLM/규칙 기반 분석, 보고서 생성까지 이어지는 통제된 실험 파이프라인**으로 보는 것이 맞다.

## 3. 현재 프로젝트의 핵심 목표

현재 프로젝트의 핵심 목표는 아래와 같이 정리할 수 있다.

### 3.1 로그 수집 중심의 실험 환경 구축

모든 외부 요청이 Apache를 통과하도록 구성하고, 그 지점에서 access/security/error 로그를 안정적으로 남기는 것이 중요하다. 이를 통해 정상 요청과 공격성 요청을 같은 기준으로 수집할 수 있어야 한다.

### 3.2 공격 재현과 baseline 비교가 가능한 실험 대상 유지

공격 탐지 실험을 위해서는 다양한 웹 공격 시나리오를 반복적으로 재현할 수 있어야 한다. 동시에, 특정 응답 metadata가 topology에 따라 어떻게 달라지는지도 확인해야 한다.

따라서 최신 구조에서는 OWASP Juice Shop만 단일 최종 대상으로 보지 않는다. Juice Shop은 대표 공격 재현 대상 또는 주 실험 대상이며, PHP sample과 OpenCart도 Apache observability와 topology baseline 확인을 위한 비교 실험 대상으로 유지한다.

### 3.3 DB 저장 및 후속 분석 가능성 확보

수집한 로그는 파일로만 보관하는 데 그치지 않고, MariaDB 같은 중앙 저장소에 정리해 저장한다. 그래야 조건 검색, 집계, 상관분석, 후보 추출, 보고서 자동화, Web UI job lifecycle 관리가 가능해진다.

### 3.4 탐지 및 분류용 데이터셋 축적

프로젝트의 활용 방향은 단순한 로그 확인이 아니라, 공격 징후 후보와 context를 분석 입력으로 축적하는 것이다. 따라서 정상 요청과 공격 요청이 모두 포함된 구조가 필요하다.

다만 Apache 로그만으로 공격 성공, 침해 성공, 노출 성공을 확정하지 않는다. 관찰 가능한 suspicious context와 candidate signal은 보존하되, 성공 여부는 별도 증거가 필요하다는 한계를 함께 기록한다.

### 3.5 합법적이고 통제된 실험 환경 유지

실험은 반드시 본인이 관리하거나 허가받은 환경에서 수행되어야 하며, 대상 애플리케이션 역시 교육용·실습용 맥락에서 설명 가능해야 한다.

## 4. 실험 대상 선정 기준

현재 프로젝트 목적에 맞는 실험 대상을 고르기 위해, 다음 기준을 우선적으로 적용한다.

1. 다양한 공격 시나리오를 반복적으로 재현할 수 있어야 한다.
2. 정상 요청과 공격성 요청을 함께 수집하기 쉬워야 한다.
3. Apache 앞단 로그 수집 구조와 결합하기 쉬워야 한다.
4. topology별 response behavior 차이를 관찰할 수 있어야 한다.
5. 설치와 재배포가 비교적 단순해야 한다.
6. 보고서에서 합법적이고 통제된 실험 환경이라고 설명하기 쉬워야 한다.
7. 추후 DB 저장, 후보 추출, LLM/규칙 기반 분석으로 확장하기 쉬워야 한다.

이 기준에 따르면, 단순 쇼핑몰 운영용 애플리케이션보다 보안 실습용 애플리케이션이 주 실험 대상에 더 적합하다. 동시에 단순 PHP sample과 실제 PHP app baseline도 로그 해석 한계를 검증하는 비교 대상으로 필요하다.

## 5. 세 실험 대상의 역할

현재 프로젝트에서 세 대상은 서로 대체 관계가 아니라 역할이 다른 관찰 대상이다.

### 5.1 PHP sample

PHP sample은 **direct Apache/PHP baseline**이다.

주요 역할:

- Apache가 직접 PHP/static endpoint를 처리하는 단순 topology 기준점
- LogFormat, parser, request_id/error_link_id 기반 access/error correlation 확인
- 단순 topology에서 `status_code`, handler, error-linked row, status/error 분포를 확인하는 기준점
- prepare candidate policy 분포를 점검하는 baseline

해석 가치:

```text
PHP sample은 단순하고 예측 가능한 baseline이다.
실제 서비스 대표성보다 로그 포맷, 파서, error correlation, candidate policy shape 확인에 적합하다.
```

### 5.2 OpenCart

OpenCart는 **real PHP app / front-controller / routed response baseline**이다.

주요 역할:

- Apache + PHP + MySQL 기반 실제 애플리케이션 topology 관찰
- `_route_=`, `redirect-handler`, directory redirect, fallback 200 관찰
- `status_code=200`이 곧 파일 존재, 공격 성공, 노출 증거가 아님을 보여주는 비교 대상
- front-controller/routed response에서 payload-like 후보와 topology context를 분리하는 기준점

해석 가치:

```text
OpenCart는 주 공격 재현 대상은 아니지만 단순 탈락 대상도 아니다.
실제 PHP app에서는 200 응답이 fallback/routed HTML response일 수 있음을 보여주는 baseline이다.
```

### 5.3 OWASP Juice Shop

OWASP Juice Shop은 **reverse proxy / backend app 기반의 대표 공격 재현 대상**이다.

주요 역할:

- Apache reverse proxy 뒤의 backend app 공격 재현
- Apache `handler=proxy-server`, backend/SPA fallback, backend response metadata 관찰
- 정상 요청과 공격성 요청을 함께 발생시키기 쉬운 주 실험 대상
- backend unavailable/proxy error 같은 availability context 관찰

해석 가치:

```text
Juice Shop은 보안 교육과 공격 재현에 적합한 주 실험 대상이다.
다만 Apache 로그는 backend 내부 인증, DB 결과, response body, 브라우저 실행 결과를 직접 보여주지 않는다.
```

## 6. OpenCart의 현재 위치

OpenCart는 무료 오픈소스 쇼핑몰 플랫폼으로서, 일반적인 전자상거래 웹서비스 구축을 실습하는 데에는 충분히 의미가 있다. 특히 다음과 같은 장점이 있다.

- 비교적 익숙한 웹서비스 구조를 제공한다.
- Apache, PHP, MySQL 조합과 잘 맞는다.
- 관리자 페이지와 상품 관리 구조를 확인하기 좋다.
- 실제 PHP app의 rewrite/front-controller 동작을 관찰할 수 있다.

그러나 현재 프로젝트는 “쇼핑몰 구축”이 아니라 “공격 로그 수집과 탐지/분류 실험”이 중심이다. 이 관점에서 OpenCart는 Juice Shop처럼 다양한 공격 시나리오를 구조적으로 제공하는 주 공격 재현 대상은 아니다.

따라서 기존의 “왜 OpenCart가 최종 대상이 아닌가”라는 판단은 다음처럼 개정한다.

- OpenCart는 주 공격 재현 대상은 아니다.
- 하지만 삭제되거나 탈락한 대상도 아니다.
- OpenCart는 front-controller/routed response baseline으로 보존 가치가 있다.
- OpenCart 관찰은 `status_code=200`, `_route_=`, `redirect-handler`가 공격 성공, 파일 존재, 파일 노출의 증거가 아님을 설명하는 데 중요하다.
- OpenCart run은 prepare candidate policy와 Apache logs-only guardrail 검증에 계속 활용할 수 있다.

즉, OpenCart의 역할은 “최종 공격 실습 대상”이 아니라 **실제 PHP app topology에서 Apache observability의 한계를 확인하는 비교 실험 대상**이다.

## 7. 대표 공격 재현 대상: OWASP Juice Shop

현재 프로젝트의 대표 공격 재현 대상은 **OWASP Juice Shop**이다.

OWASP Juice Shop은 보안 교육과 공격 재현을 위해 의도적으로 취약하게 설계된 웹 애플리케이션이다. 이 점에서 일반 쇼핑몰 애플리케이션과는 출발 목적이 다르며, 공격성 요청과 정상 요청을 함께 만들기 쉽다.

### 7.1 채택 이유

OWASP Juice Shop을 대표 공격 재현 대상으로 유지하는 이유는 다음과 같다.

1. **보안 실습용으로 설계된 애플리케이션**이기 때문이다.
2. **다양한 공격 시나리오를 한 환경에서 반복 재현**하기 쉽다.
3. **정상 요청과 공격성 요청을 함께 수집**하기 유리하다.
4. **공격 유형별 로그 축적과 라벨링 후보 구성**에 유리하다.
5. **합법적이고 통제된 실험 환경**이라는 점을 설명하기 쉽다.
6. Apache 리버스 프록시와 결합하면 **기존 로그 수집 전략을 유지하면서 backend app topology를 관찰**할 수 있다.

### 7.2 실험 관점에서의 장점

Juice Shop은 단순히 취약점이 있는 서비스가 아니라, 보안 훈련과 재현 실험에 적합하도록 잘 알려진 대상이다. 따라서 다음과 같은 이점이 있다.

- 공격 도구 또는 수동 테스트 시나리오 적용이 쉽다.
- 실험을 다시 수행했을 때 재현성이 높다.
- 공격 탐지용 로그 수집 실험의 목적을 설명하기 쉽다.
- 나중에 WAF, 포렌식 로그, 탐지 규칙, 분류 모델 실험까지 확장하기 쉽다.

주의할 점은 Juice Shop이 주 실험 대상이라는 사실이 Apache 로그 해석 한계를 없애지는 않는다는 것이다. Apache reverse proxy 환경에서 `handler=proxy-server`와 `status_code=200`이 관찰되어도 backend route 존재, 파일 존재, 인증 성공, exploit 성공을 단정하지 않는다.

## 8. Apache logs-only 해석 원칙

본 프로젝트는 Apache access/security/error log를 중심으로 분석한다. Apache 로그는 request/response metadata와 일부 error/security context를 제공하지만, 애플리케이션 내부 상태를 직접 보여주지는 않는다.

따라서 Apache 로그만으로 다음을 단정하지 않는다.

- POST body 원문
- response body 내용
- DB 조회 결과
- 브라우저에서의 JavaScript 실행 여부
- 로그인 성공, 계정 탈취, credential stuffing 성공
- 업로드 저장 성공 또는 파일 삭제 성공
- 파일 노출, 서버 침해, 명령 실행 성공
- `status_code=200` 기반 공격 성공 판정
- `response_body_bytes`, `resp_content_type`, `handler`, route 이름 기반 성공 판정
- `_route_=`, `redirect-handler`, `proxy-server` 기반 backend route 존재 또는 파일 존재 단정
- `src_ip`, `peer_ip`, `X-Forwarded-For`, `X-Real-IP`, `Forwarded` 기반 공격자 attribution 단정

사용 가능한 표현은 “요청이 관찰됨”, “payload-like 패턴이 관찰됨”, “suspicious context 후보”, “추가 확인 필요” 같은 관찰 중심 표현이다.

이 원칙은 false positive를 줄이기 위해 의심 정황을 모두 버리자는 뜻이 아니다. 관찰 가능한 suspicious evidence는 보존하되, 성공/침해/노출 확정 판정으로 승격하지 않는다는 뜻이다.

## 9. 환경 구성 방향

현재 프로젝트의 상위 구성 방향은 다음과 같이 정리한다.

### 9.1 운영체제

- **Ubuntu 22.04 LTS Server**

선정 이유:

- 장기 지원 기반이라 안정성이 높다.
- 서버 실습 자료와 참고 문서가 풍부하다.
- Apache, Docker 기반 실습과 궁합이 좋다.

### 9.2 앞단 웹서버

- **Apache2**

선정 이유:

- 외부 요청을 먼저 받아 로그 수집 지점을 일원화할 수 있다.
- Reverse Proxy 구성이 쉽다.
- 접근 로그, 보안 로그, 에러 로그를 분리해 설계하기 좋다.
- 실험 환경에서 로그 포맷을 세밀하게 제어할 수 있다.

### 9.3 애플리케이션 실행 방식

- **Docker 컨테이너 기반 실행**

선정 이유:

- Juice Shop 배포와 재실행이 단순하다.
- 실험 환경 재현성이 높다.
- Apache와 애플리케이션 역할을 분리하기 쉽다.
- 실험 중 문제가 생겨도 복구와 재배포가 비교적 간단하다.

### 9.4 실험 대상 애플리케이션

- **PHP sample**
- **OpenCart**
- **OWASP Juice Shop**

각 대상은 서로 다른 topology baseline을 제공한다. Juice Shop은 대표 공격 재현 대상이고, PHP sample과 OpenCart는 Apache observability와 topology guardrail 검증을 위한 baseline이다.

## 10. 실험 환경의 기본 구조

대표적인 Juice Shop 실험 구조는 다음과 같다.

```text
브라우저 / 점검 도구 / 실험 스크립트
                ↓
              Apache2
                ↓  Reverse Proxy
     OWASP Juice Shop (Docker, 127.0.0.1:3000)
                ↓
     access / security / error 로그 파일
                ↓
        Python log shipper
                ↓
         MariaDB (web_logs)
```

baseline 비교 실험에서는 backend app만 달라진다.

```text
PHP sample:
  Client -> Apache/PHP direct -> Apache logs -> MariaDB

OpenCart:
  Client -> Apache/PHP/MySQL + front-controller -> Apache logs -> MariaDB

Juice Shop:
  Client -> Apache reverse proxy -> backend app -> Apache logs -> MariaDB
```

이 구조의 핵심은 **모든 외부 요청이 Apache를 먼저 지나가게 하는 것**이다. 이렇게 하면 요청 수집 지점을 고정할 수 있고, 이후 DB 저장과 분석 단계도 일관되게 가져갈 수 있다.

## 11. DB-backed MVP 분석 흐름

최신 운영 방향은 DB-backed Web UI 기반 로그 분석 플랫폼이다.

기본 흐름은 다음과 같다.

```text
Apache logs
  ↓
Python log shipper
  ↓
MariaDB
  ↓
Web UI analysis_jobs 등록/조회
  ↓
Analysis Agent / worker
  ↓
run_analysis_pipeline.py full_report direct pipeline
  ↓
analysis_reports / viewer_payload / Stage2 report
```

중요한 경계:

- Web UI read-only 원칙은 **보안 결과 해석 read-only**를 뜻한다.
- DB-backed MVP에서 Web UI는 `analysis_jobs` 등록/조회와 job lifecycle 표시를 위해 제한된 DB write/read를 수행할 수 있다.
- Web UI는 Stage1/Stage2 report의 의미를 수정하지 않는다.
- Web UI는 severity/category/verdict/success를 재계산하지 않는다.
- `analysis_jobs` queue는 사용자가 등록한 분석 실행 queue다.
- `operator_queue`는 rollup 이후 사람이 검토할 관찰 대상 queue다.
- 두 queue는 목적과 위치가 다르다.

현재 MVP의 기본 `analysis_mode`는 `full_report`다.

```text
export
  -> prepare
  -> Stage1
  -> Stage2
  -> viewer_payload
```

`full_report`는 direct pipeline mode다. `sliding_window / rollup / operator_queue`는 `full_report` worker 안에 자동 포함하지 않고, 후속 `analysis_mode=windowed_triage` 흐름으로 분리한다.

## 12. 본 프로젝트에서 다루는 실험 범위

이 프로젝트에서 우선적으로 다루는 범위는 다음과 같다.

### 12.1 포함 범위

- Ubuntu 22.04 기반 실습 서버 구성
- Apache2 기반 웹 요청 수집
- PHP sample, OpenCart, Juice Shop 대상 정상 요청 및 공격성 요청 발생
- Apache access/security/error 로그 수집
- Python shipper를 통한 MariaDB 적재
- MariaDB 기반 조회, export, 후보 추출
- `full_report` direct pipeline 기반 Stage1/Stage2/viewer_payload 생성
- Web UI 기반 `analysis_jobs` 등록/조회와 결과 확인
- Apache logs-only guardrail에 따른 안전한 표현과 해석

### 12.2 제외 또는 후속 범위

아래 항목은 본 문서에서 직접 다루지 않고, 후속 문서에서 구체화한다.

- Apache VirtualHost 상세 설정 문법
- access / security / error 로그 포맷 상세
- MariaDB 테이블 정의 상세
- Python shipper 구현 상세
- 탐지 정규식과 위험도 점수 계산 상세
- Web UI 상세 구현
- worker loop/daemon 운영화
- 장시간 분석용 `windowed_triage` mode
- selected rollup 기반 brief 또는 full report 후속 경로

즉, 본 문서는 프로젝트의 **방향과 실험 대상 역할의 기준서**이며, 구현 상세는 별도 문서에서 다룬다.

## 13. 운영 및 윤리 원칙

실험 환경은 반드시 다음 원칙을 따른다.

1. 실험은 본인이 관리하거나 허가받은 시스템에서만 수행한다.
2. Juice Shop은 학습용 취약 애플리케이션이므로 외부 인터넷에 무분별하게 공개하지 않는다.
3. 정상 요청과 공격성 요청을 구분해 수집하고, 실험 기록을 함께 남긴다.
4. 로그에는 민감정보가 포함될 수 있으므로 저장 범위를 최소화하고 필요 시 마스킹 정책을 둔다.
5. Web UI, job event, error message, artifact에는 API key, `.env`, provider secret, raw provider error body를 노출하지 않는다.
6. Apache logs-only 증거만으로 성공/침해/유출을 단정하지 않는다.

이 원칙은 프로젝트의 기술적 정당성뿐 아니라 보고서의 설명 가능성을 위해서도 중요하다.

## 14. 결론

현재 프로젝트는 단순한 쇼핑몰 설치 실습이 아니라, **Apache logs-only 기반 웹 공격 관찰과 웹 로그 기반 분류 실험을 위한 분석 파이프라인 구축 프로젝트**로 정리할 수 있다.

이 목적에 맞추어 현재 방향은 다음과 같이 정리한다.

- 운영체제는 **Ubuntu 22.04 LTS Server**를 사용한다.
- 앞단 웹서버는 **Apache2**를 사용한다.
- 애플리케이션 실행 방식은 **Docker**를 우선 사용한다.
- 로그 수집의 중심 지점은 **Apache**로 통일한다.
- 수집된 로그는 후속 분석과 분류를 위해 **MariaDB 저장 및 artifact 기반 분석**을 전제로 설계한다.
- DB-backed MVP의 기본 실행 경로는 `full_report` direct pipeline이다.
- Sliding Window / Rollup / Operator Queue는 후속 `windowed_triage` 흐름으로 분리한다.

본 프로젝트의 중심은 특정 웹 애플리케이션 하나를 구축하는 것이 아니라, Apache logs-only 기반의 공격 징후 관찰, DB 저장, 후보 추출, LLM/규칙 기반 분석, 보고서 생성까지 이어지는 통제된 실험 파이프라인이다.

Juice Shop은 대표 공격 재현 대상이고, PHP sample과 OpenCart는 Apache topology와 observability guardrail을 검증하는 baseline 역할을 한다.
