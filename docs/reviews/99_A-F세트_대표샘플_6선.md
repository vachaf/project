# A~F세트 대표 샘플 6선

작성 기준: 2026-05-04  
분류: `docs/reviews/` 완료·평가성 문서  
목적: A~F 실험 세트에서 분석 품질을 설명하기 좋은 대표 케이스를 선별해, 수동 리뷰·발표·온보딩 때 비교 기준으로 사용한다.

> 이 문서는 `docs/experiments/`, `lab/`, `lab/LLM샘플검증/`의 실제 실험·리뷰 산출물을 기반으로 한다.  
> Apache logs-only 원칙에 따라 성공·침해·유출을 단정하지 않고, 관찰 가능한 로그 표면과 해석 한계를 함께 기록한다.
> A~H 실험 묶음의 docs-side summary는 [99_lab_experiment_set_summaries.md](./99_lab_experiment_set_summaries.md)를, LLM sample validation의 docs-side summary는 [99_llm_sample_validation_review.md](./99_llm_sample_validation_review.md)를 우선 참조한다. lab 원문은 장기 이관/삭제 검토 전까지 legacy lab source로 남긴다.

## 1. 사용 방법

새 Stage1/Stage2 분석 결과를 검토할 때 아래 6개 샘플과 대조한다.

```text
1. S-A: provider별 성공 해석 성향 차이를 보수적으로 제어했는가?
2. S-B: double encoding을 단계별로 복원했는가?
3. S-C: HTML entity XSS와 FP bait를 구분했는가?
4. S-D: 200 OK 다수를 민감 파일 노출 성공으로 단정하지 않았는가?
5. S-E: php://filter file disclosure intent와 taxonomy/wording guard를 적절히 처리했는가?
6. S-F: POST body 없이 auth abuse를 과도하게 단정하지 않았는가?
```

점수 체계는 [99_llm_sample_validation_review.md](./99_llm_sample_validation_review.md)에 요약된 `lab/LLM샘플검증/` 수동 리뷰 기준을 따른다.

```text
5개 항목 × 2점 = 10점 만점
9~10점: 통과
7~8점: 개선 후보
6점 이하: 재분석 필요
```

단, 이 문서의 6개 샘플은 모두 정량 채점 대상은 아니다.

| 구분 | 샘플 | 용도 |
|---|---|---|
| 정량 리뷰 샘플 | S-B, S-C, S-E, S-F | 실제 LLM 수동 리뷰 점수 대조 |
| 비교 기준 샘플 | S-A | provider 해석 성향 차이 설명 |
| 구조 개선 샘플 | S-D | candidate 과승격 없이 context-only summary를 전달한 사례 설명 |

## 3. S-A — A세트: 인증 우회 401 → 200 흐름

### 케이스 개요

```text
분석 구간: 2026-04-24 16:45 ~ 16:58 KST
전체 로그: 81건
candidate: 7건, 모두 POST /rest/user/login
구성: 401 실패 5건 + 200 처리 2건
```

실험 설계상 로그인 우회 payload가 포함된 케이스다. 다만 Apache 로그 표면만으로는 POST body 원문, JWT 발급 여부, 실제 세션 성립 여부를 직접 확인할 수 없다.

### provider별 해석 차이

| 항목 | 보수적 해석 | 적극적 해석 위험 |
|---|---|---|
| 200 응답 | 인증 관련 요청이 처리된 정황 | 인증 우회 성공으로 단정 |
| 401 연속 | 실패 반복 또는 시도 흐름 | 모든 실패를 침해 시계열로 확대 |
| 응답 크기 차이 | 401/200 response surface 차이 | 로그인 성공·토큰 발급 근거로 단정 |
| known asset 문맥 | 내부 테스트 가능성 병기 | 공격자 확정 위험 |

### 평가 질문

```text
- 401 → 200 흐름을 성공 정황으로만 표현했는가?
- Apache 로그만으로 JWT 토큰 발급 또는 계정 탈취를 확인한 것처럼 쓰지 않았는가?
- provider별 성향 차이를 모델 우열이 아니라 해석 보수성 차이로 설명했는가?
```

핵심 교훈:

```text
같은 로그도 모델에 따라 해석 성향이 달라진다.
판단 기준은 “모델이 강하게 말했는가”가 아니라 “Apache 로그만으로 말할 수 있는가”이다.
```

## 4. S-B — B세트 R2B: Double encoded SQLi

### 케이스 개요

```text
분석 구간: 2026-04-25 18:23 ~ 18:29 KST
total rows: 17
candidates: 15
supporting_events: 2
```

### 핵심 로그 표면

```text
endpoint: /rest/products/search
query: ?q=%2527%2520OR%25201%253D1%2520--
decode 1: %27%20OR%201%3D1%20--
decode 2: ' OR 1=1 --
status: 500
```

### 평가 결과

| 평가 항목 | 점수 | 근거 |
|---|---:|---|
| 성공 단정 금지 | 2/2 | SQLi 성공, DB 유출, DB dump 단정 없음 |
| 로그 한계 반영 | 2/2 | 500/text/html, 200/JSON 차이를 성공 근거로 단정하지 않음 |
| context-only 준수 | 2/2 | 저신호 temporal chain step을 supporting_events로 보존 |
| severity 적정성 | 2/2 | high candidate와 보조 문맥을 분리 |
| FP 가능성 병기 | 1/2 | 교육용 SQL 검색 분리는 됐으나 Stage2 본문 설명은 더 직접적일 수 있음 |

총점: **9/10 — 통과**

핵심 교훈:

```text
%2527은 한 번만 풀면 공격 의도가 완전히 보이지 않는다.
2단계 디코딩으로 실제 SQL payload를 복원하고, 교육용 검색과 공격 페이로드를 분리해야 한다.
```

## 5. S-C — C세트: HTML entity XSS + FP bait

### 케이스 개요

```text
분석 구간: 2026-04-25 21:30 ~ 21:33 KST
total rows: 10
candidates: 9
false_positive_review_candidates: 1
filtered_out: 1
```

### 핵심 로그 표면

```text
query: ?q=&#x3C;script&#x3E;document.cookie&#x3C;/script&#x3E;
HTML entity decode: <script>document.cookie</script>
status: 200
bytes: 30

FP bait:
query: ?q=how+to+prevent+onerror+xss+tutorial
```

### 평가 결과

| 평가 항목 | 점수 | 근거 |
|---|---:|---|
| 성공 단정 금지 | 2/2 | 브라우저 실행, 쿠키 탈취, 외부 전송 성공 단정 없음 |
| 로그 한계 반영 | 2/2 | 200/30B로 payload reflection 또는 실행 성공을 단정하지 않음 |
| context-only 준수 | 2/2 | tutorial/onerror 검색을 false_positive_review_candidates로 보존 |
| severity 적정성 | 2/2 | script/cookie 계열과 tutorial 계열을 구분 |
| FP 가능성 병기 | 1/2 | FP 구조를 Stage2 본문에서 더 직접 인용할 여지 있음 |

총점: **9/10 — 통과**

핵심 교훈:

```text
HTML entity는 우회 표현이다.
&#x3C;를 <로 복원해야 XSS 의도를 볼 수 있다.
반대로 tutorial/onerror 검색은 공격으로 과승격하지 않아야 한다.
```

## 6. S-D — D세트 R3: Directory probing burst

### 케이스 개요

```text
분석 구간: 2026-04-26 11:17 ~ 11:19 KST
total rows: 10
대표 경로: /.git/config, /.env, /admin, /administrator, /backup,
          /backups, /config, /server-status, /phpmyadmin, /manager/html
```

### 핵심 로그 패턴

```text
9건: status=200, response_body_bytes=75,002, text/html
1건: /server-status, status=403, response_body_bytes=279, text/html
```

9건의 200 응답은 민감 파일 노출 성공이 아니라 Juice Shop SPA fallback HTML 가능성을 우선 검토해야 한다. 동일 크기·동일 content-type 반복은 fallback 정황으로 볼 수 있지만, response body 원문 없이는 확정할 수 없다.

### 개선 전/후 핵심

| 항목 | 개선 전 | 개선 후 |
|---|---:|---:|
| candidate_rows | 1 | 1 |
| probing_sequence_summaries | 0 | 1 |
| filtered low-signal rows | 9 | 9 |

개선 후 핵심은 candidate를 늘리지 않고 burst probing 흐름을 context-only summary로 전달한 점이다.

```text
policy: context_only
request_count: 10
distinct_path_count: 10
status_counts: 200×9, 403×1
interpretation: probing context only, confirmed compromise 아님
```

핵심 교훈:

```text
200 OK가 9건이어도 fallback HTML이면 침해 성공으로 단정하지 않는다.
저신호 요청을 candidate로 과승격하지 않고, 흐름만 summary로 보존하는 구조가 중요하다.
```

## 7. S-E — E세트 R2B: PHP wrapper file disclosure

### 케이스 개요

```text
분석 구간: 2026-04-30
total rows: 6
주요 payload: php://filter/convert.base64-encode/resource=config.php
filtered/context: direct /config.php, /admin/config.php 접근
```

### 핵심 로그 표면

```text
endpoint: /index.php
query: ?path=php%3A%2F%2Ffilter%2Fconvert.base64-encode%2Fresource%3Dconfig.php
decode: ?path=php://filter/convert.base64-encode/resource=config.php
status: 200
response_body_bytes: 32,777
```

32,777B 응답은 일반 baseline보다 큰 응답으로 PHP wrapper 처리 또는 source/config disclosure 가능성을 검토할 만한 보조 지표다. 다만 response body 원문 없이는 실제 config.php 내용 반환, base64 인코딩 결과, DB credential 노출을 확인할 수 없다.

### 원래 수동 리뷰 결과

| 평가 항목 | 점수 | 근거 |
|---|---:|---|
| 성공 단정 금지 | 2/2 | config/source 내용 노출 성공 단정 없음 |
| 로그 한계 반영 | 2/2 | 200 + 32,777B를 성공 근거로 확정하지 않음 |
| context-only 준수 | 2/2 | direct /config.php 계열을 과승격하지 않음 |
| severity 적정성 | 1/2 | 당시 taxonomy/wording 개선 후보 존재 |
| FP 가능성 병기 | 1/2 | lab-* UA 표현이 evidence처럼 읽힐 위험 존재 |

총점: **8/10 — 통과, 개선 후보**

### 후속 보강 상태

이 샘플은 이후 개선 작업의 회귀 기준으로도 활용됐다.

```text
- suspicious_file_disclosure verdict 존재 확인
- file disclosure taxonomy 검토 문서 작성
- Stage1 lab-* / experiment-like UA guard 추가
- Stage2 stage1_carryover_rule 추가
- e_r2_php_wrapper expected rule 보강
- prepare regression 18 fixtures strict 통과
- stage dry-run regression 12 fixtures strict 통과
```

따라서 현재 이 케이스의 의미는 단순한 문제 사례가 아니라, **file disclosure intent 보존 + lab-* UA wording guard 보강이 실제로 회귀 고정된 사례**에 가깝다.

핵심 교훈:

```text
php://filter는 단순 ../ 경로 순회가 아니라 PHP stream wrapper 기반 source disclosure 시도다.
기법에 맞는 taxonomy와 보수적 성공 해석, UA 과적합 방지가 함께 필요하다.
```

## 8. S-F — F세트 R2B: Auth response delta

### 케이스 개요

```text
분석 구간: 2026-05-02
total rows: 11
candidates: 3
supporting_events: 8
auth_behavior_summaries: 1
status surface: 401 / 26B 중심
```

### 핵심 로그 패턴

```text
existing 계정 그룹:    POST /rest/user/login → 401, 26B
nonexistent 계정 그룹: POST /rest/user/login → 401, 26B
lockout-probe 그룹:   POST /rest/user/login → 401, 26B
```

Apache 로그 표면에서는 세 그룹이 동일하게 보인다. POST body 원문이 없으므로 계정 존재 여부, 비밀번호 값, lockout 발동 여부, 로그인 성공 여부는 확정할 수 없다.

### 평가 결과

| 평가 항목 | 점수 | 근거 |
|---|---:|---|
| 성공 단정 금지 | 2/2 | user enumeration 성공, lockout 발동, login success 단정 없음 |
| 로그 한계 반영 | 2/2 | POST body 미확인 한계 명시 |
| context-only 준수 | 2/2 | auth_behavior_summaries/supporting_events를 문맥으로만 사용 |
| severity 적정성 | 2/2 | 반복 401을 high로 과승격하지 않음 |
| FP 가능성 병기 | 1/2 | known asset 또는 내부 테스트 가능성은 더 명시할 여지 있음 |

총점: **9/10 — 통과**

핵심 교훈:

```text
POST body가 없는 환경에서는 계정 존재 여부조차 확정할 수 없다.
반복 auth endpoint interaction을 대표 candidate + supporting context로 나누는 구조가 보고서 신뢰성을 만든다.
```

## 10. 빠른 대조 질문

새 분석 결과물을 받았을 때 다음 질문에 답한다.

```text
1. S-A와 비교: 성공 단정이 Apache 로그 표면 근거만으로 가능한 수준인가?
2. S-B와 비교: 인코딩이 단계별로 풀려 실제 payload가 복원됐는가?
3. S-C와 비교: FP bait를 공격으로 과승격하지 않았는가?
4. S-D와 비교: 200 OK 다수를 침해 성공으로 단정하지 않았는가?
5. S-E와 비교: verdict 이름이 실제 공격 기법과 맞고, lab-* UA를 공격 근거로 쓰지 않았는가?
6. S-F와 비교: POST body 없이 말할 수 없는 내용을 단정하지 않았는가?
```

대부분 YES라면 신뢰 가능한 분석이다. 2개 이상 NO라면 재검토가 필요하다.
