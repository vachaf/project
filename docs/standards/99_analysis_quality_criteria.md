# 분석 신뢰성 평가 기준
## Apache 로그 기반 침입 탐지 시스템 — "좋은 분석"이란 무엇인가

> **핵심 명제:**  
> "우리는 공격을 '맞췄는지'가 아니라, **'왜 그렇게 판단했는지를 검증 가능한 구조로 만들었는지'**를 평가한다."

---

## 1. "좋은 분석"의 정의

> **좋은 분석이란:** Apache 로그의 가시성 한계를 인정하면서, 관찰 가능한 수치 증거(bytes, status, duration, 인코딩 패턴)를 출발점으로 삼아 Evidence → Context → Reasoning의 3단계 흐름을 통해, 비전문가도 "왜 위험할 수 있는지"를 납득할 수 있는 방식으로 공격 가능성을 서술하되 확정하지 않는 분석이다.

이 정의는 세 가지 요소를 동시에 요구한다.

| 요소 | 내용 |
|---|---|
| **보수적 해석** | 가능성을 말하되 성공·침해를 단정하지 않음 |
| **증거 기반** | bytes, status code, duration, 인코딩 패턴 등 수치 근거 필수 |
| **설명 가능성** | 로그를 모르는 사람도 판단 논리를 추적할 수 있어야 함 |

---

## 2. 평가 기준 테이블

| # | 항목 | 정의 | 왜 중요한가 | ✅ Good | ❌ Bad |
|---|---|---|---|---|---|
| 1 | **보수적 해석 원칙** | Apache 로그는 POST body / Response body를 볼 수 없으므로 공격 성공을 "확정"하지 않는다 | 가시성 한계를 무시한 단정은 오탐·과대 대응을 유발한다 | "200 OK + 32KB 응답 → 처리된 정황. 파일 노출 여부는 응답 본문 확인 필요" | "200 OK → 공격 성공 확인됨" |
| 2 | **증거 기반 판단** | bytes, status code, duration_us, ttfb_us 등 수치를 판단 근거로 명시한다 | 느낌 기반 판단은 재현·검증이 불가능하다 | "응답 32,777B는 config.php base64 인코딩 크기와 일치. 동일 IP 9건 모두 75,002B 반복 → fallback 가능성" | "응답이 크기 때문에 노출된 것 같음" |
| 3 | **인코딩 해석 능력** | URL 인코딩, null byte, HTML entity, PHP wrapper 등 인코딩 레이어를 단계별로 디코딩하여 실제 의도를 복원한다 | 인코딩을 보지 않으면 공격 의도가 로그 표면에 숨어 있다 | "`%2e%2e%2f` → `../` 디코딩 확인. `php%3A%2F%2F` → `php://filter` 복원. null byte `%00` 삽입 탐지" | "쿼리 파라미터에 이상한 문자 포함" |
| 4 | **IP 행동 맥락 (Context)** | 동일 src_ip / time window 내 요청 패턴 전체를 묶어서 해석한다 | 단일 요청은 잡음처럼 보이지만 패턴은 정찰 의도를 드러낸다 | "192.168.56.110이 120초 내 민감 경로 10개 순차 접근 → burst probing 흐름으로 해석" | "이 IP는 /server-status에 한 번 접근했음" |
| 5 | **전처리 신뢰도 (99% 필터링)** | 규칙 기반 필터가 어떤 기준으로 무엇을 제거했는지 명시하고, 중요 신호가 누락됐는지 검토한다 | 필터링 과정이 불투명하면 중요 공격이 잡음으로 탈락했는지 알 수 없다 | "low_signal_dir_probe 9건 필터링. 단, E-12(php://filter, 200, 32KB)는 같은 기준으로 탈락 — 오분류 가능성 검토 필요" | "노이즈는 모두 제거됐습니다" |
| 6 | **오탐 억제 능력** | known asset IP, 정상 UA, baseline 요청을 공격으로 과승격하지 않는다 | 오탐이 많으면 담당자가 알림을 무시하게 된다 | "HEAD / GET baseline은 candidate 미진입. known asset IP는 severity 하향 + FP note 첨부" | "HEAD 요청도 스캔 가능성이 있으므로 high severity로 분류" |
| 7 | **모델 결과 검증 (LLM 맹신 금지)** | LLM 출력이 로그 수치와 일치하는지, 단정적 표현이 없는지, verdict가 기법에 맞는지 교차 확인한다 | LLM은 확신 있게 틀릴 수 있다. 모델 출력 ≠ 사실 | "Stage1 verdict=suspicious_scan이나 php://filter는 scan이 아닌 file_disclosure 기법 → 재분류 필요" | "모델이 suspicious_scan으로 판정했으므로 스캔입니다" |
| 8 | **실행 가능한 대응 제시** | 분석 결과가 실제로 무엇을 해야 하는지로 연결된다. P0~P3 우선순위, 구체적 경로/명령 포함 | "위험합니다"만 말하는 분석은 조직을 행동하게 하지 못한다 | "P0: iptables -I INPUT -s {src_ip} -j DROP. P1: /config.php 응답 본문 즉시 확보 및 DB 크리덴셜 노출 여부 확인" | "즉시 대응이 필요합니다" |

## 3. 이중 평가 구조

### (1) 전문가 기준 — Internal Validation

전처리 파이프라인과 LLM 입력 품질을 검증한다.

```
전처리 단계 체크
  ├── 규칙 기반 필터가 무엇을 남기고 무엇을 제거했는가?
  ├── 제거된 항목 중 중요 공격 신호가 포함됐을 가능성은 없는가?
  │     예: E-12 php://filter 200 OK → low_signal_fuzzing 탈락 (오분류)
  └── 필터 기준이 명시적으로 기록되어 있는가?

LLM 입력 품질 체크
  ├── 의미 있는 데이터만 포함됐는가? (잡음 제거 완료 여부)
  ├── probing_sequence_summaries 등 맥락 필드가 포함됐는가?
  └── 입력 필드와 LLM 출력 사이에 논리적 연결이 있는가?

LLM 출력 교차 검증
  ├── verdict가 해당 기법에 적합한 분류명인가?
  │     예: php://filter → suspicious_file_disclosure (not suspicious_scan)
  ├── reasoning이 로그 수치를 실제로 인용하는가?
  └── 단정 표현("성공", "확인됨")이 없는가?
```

### (2) 비전문가 기준 — External Validation

보고서를 받아보는 사람 입장에서 판단한다.

```
설명 이해 가능성
  ├── 왜 위험한지를 기술 용어 없이 서술하는가?
  │     예: "설정 파일에는 DB 비밀번호가 있습니다. 이 파일이 노출되면..."
  ├── 근거가 숫자로 제시되는가?
  │     예: "응답 32,777 bytes — 이 크기는 config.php가 base64로 인코딩된 크기와 일치합니다"
  └── 해야 할 일이 명확한가?
        예: "지금 바로 ○○○ 팀에 연락해 이 요청의 승인 여부를 확인하세요"
```

## 4. 비전문가용 체크리스트

로그를 전혀 모르는 사람도 아래 질문으로 분석의 신뢰성을 판단할 수 있다.

| # | 질문 | YES이면 | NO이면 |
|---|---|---|---|
| ✅ 1 | 분석이 "공격 성공"이 아닌 "공격 가능성"으로 표현됐는가? | 신뢰 ↑ | ⚠️ 과도한 단정 — 재검토 필요 |
| ✅ 2 | 판단 근거에 숫자(bytes, status code, 시간, 건수)가 포함됐는가? | 신뢰 ↑ | ⚠️ 느낌 기반 판단 — 신뢰 불가 |
| ✅ 3 | URL 인코딩이나 특수 문자가 풀어서 설명됐는가? | 신뢰 ↑ | ⚠️ 공격 의도가 숨겨진 채 분석됐을 수 있음 |
| ✅ 4 | 여러 요청을 패턴으로 묶어서 해석했는가? | 신뢰 ↑ | ⚠️ 단일 로그만 봤을 가능성 — 맥락 누락 |
| ✅ 5 | "확인됨", "성공", "침해 완료" 같은 확정 표현이 없는가? | 신뢰 ↑ | 🚨 가시성 한계 위반 — 신뢰 불가 |
| ✅ 6 | 내부 IP / 알려진 자산에 대해 오탐 가능성을 병기했는가? | 신뢰 ↑ | ⚠️ 오탐 억제 실패 가능성 |
| ✅ 7 | 권고 조치가 "지금 무엇을 해야 하는가"로 명확히 제시됐는가? | 신뢰 ↑ | ⚠️ 행동 불가 보고서 |
| ✅ 8 | LLM 판정 결과를 그대로 옮기지 않고 수치로 교차 확인했는가? | 신뢰 ↑ | 🚨 LLM 맹신 — 검증 구조 부재 |

## 5. 나쁜 분석 패턴 (Anti-Patterns)

### Anti-Pattern 1 — 200 OK = 성공

```
❌ "HTTP 200 OK 응답이 반환되었으므로 공격이 성공했습니다."

왜 나쁜가:
  Apache 로그는 Response body를 볼 수 없다.
  200 OK는 서버가 요청을 "처리했다"는 신호이지, 
  공격자가 원하는 데이터를 "반환했다"는 증거가 아니다.
  fallback HTML, 빈 출력, 오류 메시지도 200으로 반환될 수 있다.

✅ 올바른 표현:
  "200 OK + 32,777B 응답. 이 크기는 config.php가 base64로 인코딩됐을 때의 
   크기와 일치하며, 실제 파일 반환 가능성을 시사한다. 
   다만 응답 본문 원문 없이는 노출 성공으로 확정할 수 없다."
```

### Anti-Pattern 2 — 단일 로그만 분석

```
❌ "이 요청 1건에서 SQL 인젝션 페이로드가 발견됐습니다."

왜 나쁜가:
  단일 요청은 맥락이 없다. 동일 IP에서 같은 시간대에
  무슨 요청들이 있었는지를 보지 않으면 정찰 흐름, 
  burst 패턴, 공격 준비 단계를 놓친다.

✅ 올바른 표현:
  "동일 IP에서 120초 내 10개 민감 경로 순차 접근 후,
   search 파라미터에 SQLi 페이로드가 삽입됐다. 
   정찰 → 공격 준비 → 실행의 흐름으로 해석 가능하다."
```

### Anti-Pattern 3 — 인코딩 무시

```
❌ "query_string에 이상한 문자들이 포함됐습니다."

왜 나쁜가:
  URL 인코딩은 공격자가 탐지를 우회하기 위해 사용하는 핵심 기법이다.
  %2e%2e%2f를 그냥 "이상한 문자"로 취급하면 
  ../  경로 탐색 공격 의도를 놓친다.

✅ 올바른 표현:
  "query_string에 %2e%2e%2f 포함 → URL 디코딩 시 ../
   경로 탐색 패턴으로 복원됨. %00 null byte 삽입으로 
   확장자 검증 우회 시도 가능성 있음."
```

### Anti-Pattern 4 — LLM 결과 그대로 믿음

```
❌ "모델이 suspicious_scan으로 판정했습니다."
   → 보고서에 그대로 기재, 추가 검토 없음.

왜 나쁜가:
  LLM은 확신 있게 틀릴 수 있다.
  php://filter 공격을 suspicious_scan으로 분류하는 것은
  LFI/파일 노출 기법을 포트스캔과 혼동한 오분류다.
  모델 출력을 수치와 교차 검증하지 않으면 
  보고서 전체의 신뢰성이 무너진다.

✅ 올바른 접근:
  "모델 verdict = suspicious_scan.
   단, php://filter/convert.base64-encode 패턴은
   LFI/파일 소스 노출 기법에 해당 → 
   suspicious_file_disclosure로 재분류 필요.
   score 14, 200 OK + 32KB 응답이 근거."
```

## 6. 분석 품질 판단 기준 요약

### ✅ 좋은 분석의 3단계 구조

```
Evidence (증거)
  └── 로그에서 직접 관찰된 수치 / 패턴
       예: status=200, bytes=32777, 
           query_string에 php%3A%2F%2Ffilter 포함,
           동일 IP 120초 내 10건 요청

         ↓

Context (정황)
  └── 증거들을 조합하여 상황을 구성
       예: php://filter + base64-encode + resource=config.php 조합은
           PHP 소스 코드를 평문으로 추출하는 LFI 기법의 전형적 패턴.
           32KB 응답은 config.php의 base64 크기와 일치.
           동일 IP가 직전 8초 내 config.php, admin/config.php에도 접근.

         ↓

Reasoning (해석)
  └── 정황을 바탕으로 가능성과 한계를 함께 제시
       예: "PHP wrapper를 통한 설정 파일 소스 탈취 시도로 해석 가능하다.
           200 OK + 32KB 응답은 서버가 요청을 처리했음을 시사하지만,
           Apache 로그만으로 실제 DB 크리덴셜 노출을 확정할 수 없다.
           응답 본문 원문 확인이 필수적이다."
```

### ❌ 나쁜 분석이 만들어지는 원인

| 원인 | 증상 | 결과 |
|---|---|---|
| 가시성 한계 무시 | "200 OK = 성공" | 잘못된 대응 우선순위 |
| 맥락 없는 단일 분석 | 요청 1건만 판단 | 정찰 흐름·burst 패턴 누락 |
| 인코딩 레이어 미해석 | "%2e%2e = 이상 문자" | 우회 공격 의도 탐지 실패 |
| LLM 출력 무검증 | verdict 그대로 보고 | 오분류가 최종 보고서에 반영 |
| 행동 미연결 | "위험합니다" 만 기재 | 조직이 무엇을 해야 할지 모름 |

## 7. 시스템 구조와 평가 포인트

```
Apache 로그 원시 데이터
        │
        ▼
┌─────────────────────────────────────────┐
│  99% 규칙 기반 전처리 (노이즈 제거)        │  ← 평가 포인트 A
│  - 필터 기준 명시적 기록 여부             │    중요 신호 누락 여부 검토
│  - 필터링된 항목 목록 보존 여부           │    E-12 사례 같은 오분류 탐지
└─────────────────────────────────────────┘
        │ (상위 1% candidate)
        ▼
┌─────────────────────────────────────────┐
│  LLM 정밀 분석 (Stage1 / Stage2)        │  ← 평가 포인트 B
│  - 입력: 의미 있는 데이터만 포함됐는가?  │    verdict 교차 검증
│  - 출력: 수치 근거 있는가?               │    단정 표현 점검
│         단정 표현 없는가?                │    인코딩 해석 포함 여부
│         verdict가 기법과 맞는가?         │
└─────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────┐
│  최종 보고서                             │  ← 평가 포인트 C
│  - Evidence → Context → Reasoning 구조  │    비전문가 체크리스트 통과 여부
│  - 비전문가도 이해 가능한가?             │    실행 가능한 P0~P3 조치 존재 여부
│  - P0~P3 우선순위 조치 명시             │
└─────────────────────────────────────────┘
```

## 8. 발표용 핵심 요약

> **"우리는 공격을 '맞췄는지'가 아니라, '왜 그렇게 판단했는지를 검증 가능한 구조로 만들었는지'를 평가한다."**

이 기준이 의미하는 것:

- **탐지율**이 아닌 **판단 추적 가능성**이 품질의 척도다
- 분석 결과가 틀려도 괜찮다. 하지만 **왜 그렇게 판단했는지 설명할 수 없으면 안 된다**
- Apache 로그의 한계를 인정하는 것이 신뢰성의 출발점이다
- LLM이 말했다는 것은 근거가 아니다. **수치가 근거다**
